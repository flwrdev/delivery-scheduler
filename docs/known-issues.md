## Standing action items

- **FULLY RESOLVED + LIVE-VERIFIED (2026-08-16) — Lalamove webhooks confirmed non-functional for this merchant's orders; design pivoted to polling-only, then confirmed working end to end on a real production order (ADR-16).** The original plan was webhook-primary with `matchAndRecordLalamoveOrder` phone-matching a Lalamove `ORDER_CREATED` push. Live-tested the same day it shipped: with the webhook correctly registered and a real test delivery in progress (driver assigned, then cancelled), the Lalamove Partner Portal's own "Webhook attempts" log recorded **zero** order-related events — while an unrelated `WALLET_BALANCE_CHANGED` event delivered fine on the same URL/credentials. Direct `getOrderStatus(orderId)` reads, by contrast, succeeded for that same manually-booked order. Conclusion: Lalamove's push webhooks are tied to orders placed via the API — a platform characteristic, not something fixable from our side. **Fix:** phone-matching and `ORDER_CREATED` handling were deleted outright; the merchant now pastes the real Lalamove Order ID into the "Mark as fulfilled" modal, and `internal.lalamove-poll.ts` — wired to the Google Cloud Scheduler job `delivery-scheduler-lalamove-poll` (every 30 min) — is the mechanism that actually runs. Two more bugs were found and fixed the same day during live testing: (1) the poller's original 2-hour staleness gate (a sensible fallback-behind-a-working-webhook design, wrong once polling became primary — it made a delivery completed within 2 hours of being recorded invisible to the poller) was removed, every non-delivered row is now checked every cycle; (2) the Lalamove app displays order ids prefixed with `#` (a URL fragment delimiter), which merchants naturally copy — a pasted `#3563144148557194173` broke the HMAC signature (signed the full string, but fetch's URL parser silently dropped everything from `#` onward before sending), fixed by `sanitizeLalamoveOrderId()` stripping a leading `#`. **Live-verified 2026-08-16 on real production order `#4126`** ("Crimson Whisper" bouquet, customer Jun Carbonell): Lalamove order `3563089414056014043` booked → id pasted into "Mark as fulfilled" → courier completed the delivery → the scheduled poller detected `COMPLETED` and called `fulfillmentEventCreate` → Shopify Admin now shows the order **"Delivered," Sunday August 16 2026, with the Lalamove order id as the tracking number** — confirmed visually in Shopify Admin, zero manual clicks. See the ADR-16 addendum in `decisions.md` for the full trail. This item is closed. **Follow-up same day:** the poll interval was cut from 30 to 10 minutes (a real gap the merchant hit — a delivery completed on Lalamove between two scheduled polls and wasn't caught until manually re-triggered) — see the Cloud Scheduler job `delivery-scheduler-lalamove-poll`'s current schedule, not the 30-minute figure above.

- **OPEN — Pending Lalamove Enterprise account manager outreach re: enabling order-status webhooks (2026-08-16).** The merchant's Lalamove account was upgraded to Enterprise with a dedicated Account Manager (Abigail Aben) assigned. Given the ADR-16 finding above — that push webhooks never fire for web-booked orders on this account — the merchant is reaching out to ask whether Lalamove can enable `ORDER_STATUS_CHANGED` (and ideally `ORDER_CREATED`) webhook delivery for orders booked through the web "Place Order" flow, not just API-created ones, now that the account has direct support access. **If Lalamove enables this:** the webhook route (`webhooks.lalamove-tracking.ts`) is already built, deployed, and correctly signature-verifying — it just needs the phone-matching-era discovery logic re-added (or a simpler variant, since `recordLalamoveOrderId` already exists for the merchant-pasted-id path) to auto-populate `LalamoveTracking` rows from an `ORDER_CREATED` push instead of requiring the manual paste. The 10-minute poller should stay as a fallback either way. **Until then:** the manual-paste + polling design (above) is what's live and working — do not treat this as blocking or broken, just as a possible future automation improvement.
  - **Two alternatives were explored and deliberately NOT built, same session:** (1) **Scraping the tracking share-link page** (`share.lalamove.com/?<token>...`) — confirmed live that the rendered page DOES show both the delivery status text ("Completed Today, 2:48 PM") and the real numeric Order ID as plain, extractable text, BUT the page is a client-side-rendered SPA (empty initial HTML, `<div id="root">`) — reading it requires a headless browser (Puppeteer/Playwright + Chromium), not a simple HTTP fetch. Rejected: real recurring cost (~$30-50+/mo for a hosted headless-browser service, or a heavier/slower Cloud Run container to self-host one), fragility (unversioned consumer-facing page, could break on any Lalamove frontend change with no notice), and likely outside the intended use of that page (built for humans, not machine polling) versus the documented, stable, already-integrated Open API. (2) **A Chrome extension monitoring the tracking page** — rejected for a more fundamental reason: it would only run while the merchant's Chrome browser is open and the computer is on, a real reliability *downgrade* from the current server-side poller (Cloud Run + Cloud Scheduler), which runs 24/7 independent of the merchant's own machine.
- **RESOLVED + STANDING RULE — 2026-08-01 Neon data wipe: root cause was `prisma migrate diff` pointed at the LIVE database as its shadow DB.** During the Messenger phase-3 migration authoring, `npx prisma migrate diff --from-migrations … --shadow-database-url <DIRECT_DATABASE_URL from .env>` was run with the **production** Neon URL as the shadow database. Prisma RESETS the shadow database to replay migrations — this wiped `neondb` (dropped `_prisma_migrations` + all row data; tables were left recreated but empty). Confirmed from the raw session transcript: the two `migrate diff --shadow-database-url` invocations ran at **2026-08-01T04:56:44.342Z and 04:57:05.261Z UTC (12:56:44 PM and 12:57:05 PM Manila)**, 21 seconds apart — the wipe happened in that window, not the earlier ~11:43 AM–12:15 PM estimate this entry originally carried (that was a rough guess made before the transcript was checked; the Neon time-travel snapshot at 11:42:58 AM predates the wipe and was still fully intact, which is why it was the recovery point). Consequences and repairs, all completed same-day: (1) new revisions failed to boot with P3005 → repaired by baselining the pre-existing migrations (`prisma migrate resolve --applied` ×N) + `migrate deploy`; (2) `Session` re-minted itself via app auth; (3) both `DeliveryScheduleConfig` rows were recovered via **Neon time-travel query** (state as of 11:42:58 AM, minutes before the 6-hour Free-plan window closed) and re-inserted verbatim — snapshot preserved at [docs/backups/delivery-schedule-config.2026-08-01.json](./backups/delivery-schedule-config.2026-08-01.json). **STANDING RULE: never pass a real database URL as `--shadow-database-url`, and never run `prisma migrate dev`/`diff --shadow-database-url` against `.env` URLs in this repo — hand-write migration SQL or use a throwaway local Postgres.** If P3005 ever reappears on deploy, repeat the baseline procedure and check the Neon time-travel window IMMEDIATELY (it is only 6 hours on the Free plan).
- **FINAL FORENSIC ADDENDUM (2026-08-17) — read-only production DB audit closes the 2026-08-01 Neon incident record above; see the matching verification-log.md row for the full query-by-query detail.** Appended on the merchant's explicit request for primary evidence over narrative. **Confirmed by direct, current-state evidence:** all 8 rows in `_prisma_migrations` — including `20240530213853_create_session_table`, filename-dated May 2024 — carry `started_at >= 2026-08-01T05:43:08Z`, and the first three carry `applied_steps_count: 0` (the exact signature of a `migrate resolve --applied` baseline, not an original deploy). This is present-tense proof the migration history was found reset and rebaselined starting 2026-08-01T05:43:08Z (1:43:08 PM Manila) — **~46 minutes after** the two `migrate diff --shadow-database-url` commands, timestamped 2026-08-01T04:56:44.342Z and 04:57:05.261Z UTC in the raw session transcript. **What this does NOT claim:** it does not claim the `migrate diff` commands were directly observed dropping/resetting the tables — no log line captures the reset itself happening. What is proven is narrower: production's `DIRECT_DATABASE_URL` was supplied as the shadow-database parameter, and the migration history was found reset shortly after; the causal link relies on Prisma's documented behavior for that flag plus the timing fit. `pg_stat_user_tables` counters and `pg_class.relfilenode` clustering are supporting signals only, not standalone proof. This is the closing entry for this incident record — no further changes expected absent new evidence.
- **TECHNICAL SAFEGUARD ADDED (2026-08-17) — the STANDING RULE above is now enforced by a Claude Code hook, not documentation alone.** `.claude/settings.json` (committed, project-wide) registers a `PreToolUse` hook on `Bash` (`.claude/hooks/block-shadow-db.cjs`) that inspects every Bash command before it runs and denies it outright if it matches `--shadow-database-url` or `prisma migrate dev` — the two patterns responsible for the 2026-08-01 wipe. Live-tested 2026-08-17: a real Bash tool call containing `--shadow-database-url` was blocked before execution with the incident explained in the denial reason; `npm run setup`, `prisma migrate deploy`, `prisma migrate status`, `prisma generate`, and unrelated commands all still run normally. This closes the gap the documentation-only STANDING RULE left open — a future session (or human) typing the dangerous command no longer depends on having read known-issues.md first.
