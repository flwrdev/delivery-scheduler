- **2026-07-13 (Customer Email SHIPPED — in-app compose modal, live-verified happy + failure paths)** — The locked design ([customer-email-design.md](./customer-email-design.md), ADR-11) is implemented on `feature/customer-email`: the panel's "Send email" now opens an **in-app Polaris compose modal** (To read-only = the order's customer email, subject prefilled `Order #XXXX`, ≈6-row plain-text body) and sends server-side through the merchant's business mailbox — new service [`send-customer-email.server.ts`](../app/services/send-customer-email.server.ts) (nodemailer, `mail.privateemail.com:465` SSL, lazy singleton transport, auto-BCC-self, `logger: false`) + a `sendEmail` op on `/app/orders` (recipient re-read server-side from the order — never client-supplied; **zero order writes**, api.md §2 unchanged). **Live smoke found one real bug**: op failures originally returned HTTP 502, and **Cloudflare replaces origin 502/504 bodies with its branded HTML error page** — the fetcher got HTML instead of JSON and the embedded iframe blew up to "Bad gateway". Fixed: upstream failures now return `200 + ok:false` (same shape as the bulk ops); validation stays 4xx. Verified live: happy path (success toast, mail arrived in the customer inbox from "The Flowercart", Gmail API-confirmed) and wrong-password path (in-modal error banner, typed message preserved, no crash). 19 new unit tests (57 total); new dep `nodemailer`; env vars per design §3. → [full entry](./verification-log.md)

- **2026-07-12 (Customer Email design LOCKED — docs-first, implementation deferred past V2 closeout)** — New design doc [customer-email-design.md](./customer-email-design.md): the panel's "Send email" will become an **in-app compose modal sent server-side through the merchant's business mailbox (Namecheap Private Email, plain SMTP via nodemailer)** — the native-admin-style flow the merchant originally expected. Research first (sources in the design doc): the Gmail API path was REJECTED — `gmail.send` is a Google "sensitive" scope needing weeks-long app verification, and testing-mode refresh tokens die every 7 days; Private Email needs neither (plain SMTP AUTH, 500/hr limit, branded sender). Merchant-locked decisions: compose modal in the panel now (service reusable for the planned Communications page), auto-BCC-self for sent copies, server-side recipient lock (order id → re-read customer email; never client-supplied), no order-state writes, plain text. Merchant-only setup gated stop-and-ask: SMTP creds → Secret Manager + Cloud Run env. **No code in this entry**; ships later on `feature/customer-email`, only after the §8-FST V2 closeout.

- **2026-07-12 (S9 round 2: mailto abandoned → Gmail compose URL, live-verified)** — The merchant's §8-FST re-run passed S10–S13 but failed S9 again: "Send email" did nothing. Root cause is **outside the app** — the machine's OS mailto handler is `ChromeHTML` (Chrome itself) and no webmail handler is registered inside Chrome, so the mailto handoff is circular and silently dropped; no mailto-based fix can ever work there. On the merchant's pick (over a provider-choice popover and copy-to-clipboard), "Send email" is now a **declarative external link to the Gmail compose URL** (`mail.google.com/mail/?view=cm&fs=1&to=<customer>&su=Order <name>`, `external: true` — the same sanctioned new-tab path as "View order status page"). Gmail-specific by design: single-tenant app, Gmail-based merchant. Live-verified: click → new tab → compose with To + subject prefilled, admin intact, no console errors. Audit §G round-2 addendum has the full trail. → [full entry](./verification-log.md)

- **2026-07-12 (§8-FST round-1 bug sweep — S9–S13 fixed + live-verified same day)** — The merchant's two confirming smoke runs surfaced five bugs; all root-caused in source, fixed on explicit instruction, and re-verified live in the embedded dev app before commit. **S9 (blocking):** "Send email" opened a blank "Untitled" tab — mailto + `_blank` is unreliable in Chrome AND Polaris ActionList silently ignores the item `target` prop, so the fix triggers the mailto on the **top frame** from `onAction` (no crash, no orphan tab; compose depends on the machine's mail-handler setting). **S10:** archived orders stayed in "All" — the loader sent no `status:` term and GraphQL defaults to all orders; every main view now queries `-status:closed` (NOT `status:open`, which would also hide cancelled orders — dev-store probe), and a new **Archived** tab (`status:closed`) keeps Unarchive reachable. **S11:** cancelled orders showed "Unfulfilled" — new `fulfillmentBadge()`/`isCancelled()` render a critical **Cancelled** badge in list + panel + Delivery section, suppress Today/Overdue chips, and drop cancelled from unfulfilled counts. **S12:** "This week" was Monday-start so Sundays emptied it — now Sunday→Saturday calendar week. **S13:** search Cancel was a no-op (`IndexFilters` never calls `onQueryClear` on cancel) — now wired to the immediate query clear. Audit §G has the full table. → [full entry](./verification-log.md)

- **2026-07-12 (Bouquet email round-1 FAILED → F5: the Liquid snippet, not the app)** — The first live test of the "View bouquet photo" email link came back without the link — and the evidence cleared the app: the raw email HTML has no bouquet section at all, while the order's `custom.bouquet_photo` metafield had been in place **~85 minutes before** the send (write-before-fulfillment confirmed working). Root cause (**audit F5**): notification-template Liquid hands back order metafields as **raw values**, not theme-style drops — so the provided snippet's `.value` returned nil and the conditional never fired. Fix is merchant-side only: a corrected drop-safe snippet (`…value | default: metafields.custom.bouquet_photo`), plus a placement note (move it below the actions block's closing `{% endif %}`). Re-test can reuse order #1009 (metafield already present); "Send test email" won't work for this (sample data has no metafield). No app code changed. → [full entry](./verification-log.md)
