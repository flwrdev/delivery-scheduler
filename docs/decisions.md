## ADR-1: Delegate courier dispatch to the official Shopify Lalamove app

**Source:** verification log 2026-07-04.

**Context:** The app previously carried a bespoke Lalamove integration (`lalamove.*` metafields, a `webhooks.lalamove.ts` callback, an `orders/cancelled` webhook, `app/lib/lalamove.server.ts`, and in-drawer dispatch/quote UI). The store now has the official Shopify Lalamove app installed, which duplicates and supersedes that functionality.

**Decision:** Remove the custom Lalamove integration entirely and let the official Shopify Lalamove app handle all last-mile courier booking. This app now does delivery-date/time-slot **scheduling only**.

**Consequence:** No `lalamove.*` metafields, no custom dispatch UI, no Lalamove callback webhook, and no `orders/cancelled` webhook remain. Do **not** reintroduce any of them; coordinate courier work through the official app instead. The team deliberately left access scopes (`read/write_fulfillments` etc.) intact because the manual `markFulfilled` bulk action still uses them; removing them would force merchant re-consent.

## ADR-2: Verify the App Proxy signature manually on the products route

**Source:** verification log 2026-07-02.

**Context:** `apps.schedule-rules.products.ts` paginates collection products for the theme's "Show more" button, public catalog data that never needs a merchant session. Calling `authenticate.public.appProxy` always resolves an offline session from Prisma/Neon (per Shopify's own docs); combined with Cloud Run scale-to-zero + Neon Free auto-suspend, that caused a double cold-start on the first hit of the day.

**Decision:** Verify the App Proxy `signature` by hand via `app/lib/verify-app-proxy.server.ts` (`verifyAppProxySignature`: HMAC-SHA256 over sorted `key=value` query params excluding `signature`, keyed with the existing `SHOPIFY_API_SECRET`, plus a 5-minute timestamp freshness check) instead of calling `authenticate.public.appProxy`.

**Consequence:** No Prisma/Neon session lookup on this route, so no compounded Neon+Cloud Run cold start. This is the **only** App Proxy route that does not call `authenticate.public.appProxy`; every other one still does and must. No new secret is needed; the same `SHOPIFY_API_SECRET` signs the proxy request.

## ADR-3: Call the Storefront API directly (not Admin) on the products route

**Source:** verification log 2026-07-02.

**Context:** The same products route originally hit the Admin API and derived `availableForSale` manually via an `isBuyable()` check (`status === "ACTIVE"` + `tracksInventory`/`totalInventory`). The Admin API path is heavier than needed for public catalog data.

**Decision:** Call the **Storefront API** directly via `fetch` with a private access token (`SHOPIFY_STOREFRONT_ACCESS_TOKEN`), and read `availableForSale` directly off the Storefront `Product` object.

**Consequence:** The team deleted the manual `isBuyable()` filter (not just simplified it): the Storefront API only ever returns products published and purchasable on the calling sales channel, so the filter is redundant. The response contract (`{ products, nextCursor, hasNextPage }`) is unchanged. Requires a one-time manual setup of `SHOPIFY_STOREFRONT_ACCESS_TOKEN` in both `.env` and the Cloud Run secret (see `docs/cloud-run-neon.md` §6). No fallback to Admin: if the token is unset the route returns `502`.

## ADR-4: Centralize `RESCHEDULED_ORDER_TAG` in `app/lib/constants.ts`

**Source:** verification log 2026-06-07.

**Context:** The reschedule-lock tag `"resched"` was duplicated as a raw string literal in both reschedule routes (`apps.schedule-rules.reschedule.ts` and `public.customer-account.reschedule.ts`). A divergent literal in one place would silently break the single-online-reschedule lock.

**Decision:** Export `RESCHEDULED_ORDER_TAG` from `app/lib/constants.ts` and import it in both reschedule routes.

**Consequence:** One source of truth for the lock primitive. Do not reintroduce the `= "resched"` literal per route. This is the repo's one evidenced "single-source shared constants instead of duplicating literals" convention (see [development.md](./development.md#coding-conventions--not-yet-documented)).

## ADR-6: Remove the products route's session-storage dependency

**Source:** former `docs/decision-log.md` entry dated 2026-07-02 (migrated here).

**Context:** The `/apps/schedule-rules/products` route (unrelated to delivery scheduling; it paginates collection products for the theme's homepage "Show more" button) had a 4-7 second delay on the first click of the day; subsequent clicks were fast. Root cause: a double cold start. Cloud Run scales to zero (`--min-instances 0`) and Neon Free Postgres auto-suspends when idle; `authenticate.public.appProxy()` always resolves an offline session from Prisma/Neon session storage before handing back either an `admin` or `storefront` client, even though this route never needed a merchant session, only public catalog data.

**Decision:** Removed the route's dependency on session storage (Neon/Prisma) by (1) verifying the App Proxy `signature` manually instead of calling `authenticate.public.appProxy`, via a new helper `app/lib/verify-app-proxy.server.ts`, and (2) calling the Storefront API directly instead of the Admin API. *(This is the same change captured at a design-decision altitude by ADR-2 and ADR-3 above.)*

**Investigation findings** (confirmed against Shopify's current docs via the dev-docs MCP tool and `validate_graphql_codeblocks`, not assumed from training data):
- App Proxy signature algorithm: HMAC-SHA256 hex digest over the query params (excluding `signature`), sorted by key, multi-value params joined with `,`, concatenated with **no separator** between pairs (not `&`; Shopify's own reference implementation does a plain `.join` with no delimiter), keyed with the app's shared secret. That secret is the same `SHOPIFY_API_SECRET` this app already uses elsewhere (`app/shopify.server.js`); no new secret is needed for signature verification itself.
- Storefront API's `Product.availableForSale` is a direct top-level Boolean field; there's no need to derive it from `tracksInventory`/`totalInventory` the way the Admin API version required.
- Storefront's `Product.compareAtPriceRange` reuses the *same* `ProductPriceRange` type as `priceRange` (both expose `.minVariantPrice`), unlike Admin's separate `ProductCompareAtPriceRange.minVariantCompareAtPrice`: a simpler mapping than the original Admin-based code.
- The Storefront API is inherently scoped to what's published/purchasable on the calling sales channel; it excludes draft/archived/unpublished products automatically. The team therefore deleted the old manual `isBuyable()` filter (`status === "ACTIVE"` + inventory check) rather than just simplifying it: the filter is redundant against this API.

**Trade-offs:** No change to the response contract: `{ products, nextCursor, hasNextPage }` and each product's shape are unchanged, so the theme's `collection-show-more` custom element (in the separate `live-theme-clean` repo) needed zero changes. Requires one new manual setup step: a **private** Storefront Access Token (`SHOPIFY_STOREFRONT_ACCESS_TOKEN`), created via Shopify Admin → Develop apps, configured in `.env` and the Cloud Run secret. No fallback to the old Admin API path: if the token is ever missing, the route returns `502` rather than silently degrading.

**Incident note:** While verifying the token's env var was wired correctly, a `grep` against `.env` that matched the whole line echoed its value into a terminal/tool-output transcript, value included. The user is rotating the token as a precaution. Not a code defect, a process reminder: when checking that an env var is *set*, check the key only, never `grep`/`cat` a `.env` file's values into a transcript.

**Verification:** `npm run typecheck` and `npm run lint` clean on all touched/added files. `npm test`, with `test/verify-app-proxy.server.test.ts` added (8 cases), runs 31/31 total tests green (23 pre-existing + 8 new).

**Scope note:** This still leaves a plain Cloud Run container cold start possible on the first hit of the day (just not the compounded Neon+Cloud Run one). The stronger long-term fix, the theme calling the Storefront API directly from the browser and bypassing this backend entirely, was scoped and deferred to a separate task ("Option B"). See [`docs/superpowers/plans/2026-07-02-theme-storefront-api-direct-migration.md`](superpowers/plans/2026-07-02-theme-storefront-api-direct-migration.md) for the prepared implementation prompt. **That work happens in the separate `live-theme-clean` theme repo, not here.**

**Status:** Live. `SHOPIFY_STOREFRONT_ACCESS_TOKEN` configured in both local `.env` and the Cloud Run secret.

## ADR-8: Refactor in place (not greenfield rebuild) for Order Operations V2

**Source:** [proposals/orders-refactor-vs-rebuild.md](./proposals/orders-refactor-vs-rebuild.md) (read-only audit, 2026-07-08).

**Context:** Order Operations V2 adds write paths the current `/app/orders` dashboard lacks (reschedule via `custom.date`/`custom.time_slot`/`reschedule_history`, mark COD paid), plus a Today-first view and keyboard-driven flow. The question was whether to refactor `app.orders.tsx` + `OrderDrawer.tsx` in place or rebuild in a new namespace reusing only shared utilities.

**Decision:** Refactor in place. Basis (from the audit): reusability scorecard of **64% keep-as-is / 34% salvage-with-rework / 2% delete** over 4,633 lines; `markFulfilled` is already implemented in the existing action handler (`app.orders.tsx:709-870`), proving the per-op pattern absorbs complex writes; and the reschedule domain services (`syncOrderDeliveryMetafields`, `syncOrderDeliveryScheduleTag`, `validateDeliverySelection`, `RESCHEDULED_ORDER_TAG`) are shared with the live customer reschedule route in this same repo. A greenfield namespace would import the identical services while duplicating the loader, query, table, and CSS.

**Consequence:** Phase 1+ extraction work (modals → components, KPI/filter/bulk-action hooks, dead-export deletion, docs-drift fixes D1/D2 + the development.md dev-boot note) proceeds against the existing route. No parallel second dashboard will be built or maintained.

**Exit criteria: the recommendation flips to greenfield if any of these holds (verbatim from the proposal):**

1. **If V2's UX is decided to be a queue/kanban, not a table,** then the table
   JSX (the biggest salvage item) stops being reusable and the split degrades to
   roughly 50% keep / 15% salvage / 35% rewrite, at which point greenfield wins.
2. **If Phase-1 extraction reveals the Polaris web-component modal wiring
   (`commandFor`/`command` attributes + `getElementById` show/hide) breaks when
   modals move to child components** and has no clean fix, the salvage bucket's
   "mechanical" premise fails.
3. **If the dashboard must stay bit-frozen during V2 development** (e.g. peak
   season freeze), refactor-in-place violates the freeze by definition.

**Status:** Adopted. Phase 0 (tree cleanup + baseline) done 2026-07-08; Phase 1 not yet started.

## ADR-9: Adopt Polaris React for `/app/orders` as a conscious bet against the web-components direction

**Source:** verification log 2026-07-11 (design finalization); [orders-ops-v2-ux.md](./orders-ops-v2-ux.md).

**Context:** The current `/app/orders` page is built on Polaris **web components** (`s-*`), Shopify's stated go-forward direction for App Home surfaces. The V2 goal is interaction parity with the native Shopify Admin Orders page (saved-view tabs, `IndexFilters`, `IndexTable` with bulk bar, sortable columns). The web-components library has no equivalent of `IndexFilters`/`IndexTable`/`useIndexResourceState` today, and its command-API modal wiring is the root cause of the S1/S2/S6 defect cluster (see [orders-ops-v2-audit.md](./orders-ops-v2-audit.md)).

**Decision:** Rewrite the `/app/orders` presentation layer in Polaris **React** (`@shopify/polaris` v13). This is a deliberate bet AGAINST Shopify's web-components strategic direction, justified by component maturity: the interaction-parity goal is unachievable with the web-components set today.

**Consequence / exit cost:** A future re-migration to web components (if/when they reach feature parity) is bounded to presentation-only work because the loader/action/services/business logic stay frozen and Polaris React types must not leak into `order-utils.ts` or the services. If Shopify sunsets Polaris React for embedded apps before web components reach parity, revisit this decision.

**Status:** Accepted (design locked 2026-07-11; Phase 0 shipped, Phases 1-5 pending).

## ADR-10: Merchant reschedule is an administrative override; ONE shared service defines the reschedule write sequence

**Source:** verification log 2026-07-11 (design finalization); [orders-ops-v2-ux.md §5](./orders-ops-v2-ux.md).

**Context:** Orders Ops V2 Phase 4 makes `/app/orders` the **4th delivery write path** (merchant manual reschedule). The principal-architecture review found two structural problems with the original "reuse the same services" plan: (1) the customer reschedule route (`public.customer-account.reschedule.ts`) actually **inlines** its whole write orchestration — it does NOT call `syncOrderDeliveryMetafields`/`syncOrderDeliveryScheduleTag`, and it does NOT update the legacy mirror metafields (`delivery.date`, `delivery.time_slot`, `sidekick.delivery_date`), leaving them stale after every customer reschedule; (2) `validateDeliverySelection` bundles the cutoff/prep/`maxDays` date-window policy with the data-integrity checks, so reusing the engine as-is would block the merchant path's primary use case (phoned-in too-close reschedules).

**Decision (merchant policy, stated 2026-07-11):** The merchant manual reschedule is an **administrative override**: customer self-service restrictions (`resched` lock, `≥2-days` gate, `FULFILLED` gate, cutoff/prep window) apply ONLY to the Customer Account flow and never bind the merchant. Data-integrity validations (date format, slot exists, blocked dates/slots) stay hard-enforced; slot capacity becomes **warn + explicit confirm override** (the merchant is the final authority on their own capacity). One new shared service `rescheduleOrderDelivery()` (`app/services/reschedule-order-delivery.server.ts`) defines the entire write sequence; the customer route is refactored onto it, and BOTH sources then write the legacy mirrors, fixing the stale-mirror inconsistency.

**Explicitly declined (accepted risks, recorded so they are not re-litigated):** no pre-write race-guard on the merchant op; no `reschedule_history` re-read before append (concurrent customer+merchant writes can lose one history event); no staff actor identity in history events (`source: "merchant"` is the only attribution); no fulfilled-order confirm dialog.

**Consequence:** When Phase 4 ships, api.md §2 gains a 4th write path, the `/app/orders` caveat is removed, and the Customer Account reschedule row changes (mirrors now written). Any future change to a data-integrity validation requires documented reasoning + impact analysis in the docs set **before** implementation.

**Status:** Accepted (design locked 2026-07-11; implementation pending Phase 4).

## ADR-11: In-app customer email via the merchant's business SMTP mailbox (Gmail API rejected)

**Source:** [customer-email-design.md](./customer-email-design.md) (design locked 2026-07-12, merchant-approved); verification log 2026-07-13 (implementation + live smoke).

**Context:** The panel's "Send email" went through three shapes during Orders Ops V2 (§8-FST audit §G): `mailto:` (dead on machines with a circular OS handler chain), then a Gmail-compose-tab link (reliable, but leaves the app and assumes the merchant's Gmail). The merchant's actual expectation was the native Shopify-admin experience: compose inside the app, system sends the mail.

**Decision:** Server-side send through the merchant's **business mailbox on Namecheap Private Email via plain SMTP AUTH** (nodemailer, `mail.privateemail.com:465` SSL), exposed as the `sendEmail` op on `/app/orders` + a compose modal in the details panel. **The team rejected the Gmail API**: `gmail.send` is a Google "sensitive" OAuth scope requiring app verification (privacy policy, homepage, weeks-long review), and testing-mode refresh tokens expire every 7 days, unworkable for a single-tenant custom app. Guardrails: recipient locked server-side (op takes an order id and re-reads the customer email; never client-supplied), auto-BCC to the sender mailbox (Private Email SMTP sends don't land in webmail Sent), plain text only, **zero order-state writes** (api.md §2 unchanged), config-gated env vars (clear error when unset).

**Learned in live smoke (2026-07-13):** op failure responses must be `200 + ok:false`, never 5xx. Cloudflare (the dev tunnel, and any CF-fronted deployment) replaces origin 502/504 bodies with its branded HTML error page, which breaks the fetcher JSON contract and blows up the embedded iframe. Validation errors stay 4xx (passed through untouched).

**Consequence:** New dependency `nodemailer`; new env vars `EMAIL_SMTP_HOST/PORT/USER/PASSWORD` + `EMAIL_FROM_NAME` (local `.env` dev, Secret Manager → Cloud Run prod); `/app/orders` gains a non-order-mutating outbound side effect. The send service is deliberately reusable for the planned Communications page.

**Status:** Accepted; shipped on `feature/customer-email`, live-verified 2026-07-13 (happy + wrong-password failure paths).

## ADR-12: Booked counts move to metafield-date-scoped queries + a short in-memory cache (DB counter deferred)

**Source:** [scheduler-v2-audit.md](./scheduler-v2-audit.md) (2026-07-15) + [scheduler-v2-ux.md §5](./scheduler-v2-ux.md); merchant decision D1, 2026-07-15.

**Context:** The architecture principle was "booked-slot counts are computed live via Admin GraphQL on every call, never cached locally." In practice the implementation (`loadAutomaticBookedCounts`) scanned up to 20×250 = 5,000 orders filtered by `created_at` lookback on **every** rules read, including every storefront cart view (RACE-03/PERF-1), while still being wrong: it missed old orders rescheduled into future dates (the lookback is order age, not delivery date), silently truncated past page 20, matched slots by case-sensitive exact string, and failed open to `booked: 0` on any Admin API error. Meanwhile the `orders/create` webhook compared against the stale persisted `booked: 0`, so capacity was never actually enforced at order creation (DEF-3).

**Decision (merchant, D1):** The service computes counts from **one Admin GraphQL orders search filtered by `metafields.custom.date:<date>` terms over the future capacity-tracked dates** (the same metafield-filter mechanism `/app/orders` already uses), matching **metafields only** through one canonical normalizer, excluding cancelled orders, and **memoizes the raw matched bookings in-process per shop for 60 seconds** (which also makes exclude-self-on-reschedule free). The principle is amended, not abandoned: booked counts are still **never persisted** and never authoritative-in-DB; they are live-derived with a short TTL. A Postgres counter with atomic increment (the full RACE-02 oversell fix) is **explicitly deferred** until oversell is observed to be a real business problem.

**Explicitly accepted:** up to 60s staleness in every capacity check; the TOCTOU oversell window remains (unchanged from today; there was never a reservation primitive); scan failure still fails open for sales continuity, but now surfaces as a real `countsMeta.status` warning in admin instead of a fabricated green pill.

**Consequence:** `docs/architecture.md`'s "never cached" wording must be updated when Phase 2 ships; `getScheduleRulesWithBookedCounts` keeps its signature (additive `countsMeta`); the `created_at`-lookback scan and the tag/attribute booking heuristics are deleted; pre-V2 orders whose metafield sync was blocked are consciously not counted (D4's always-sync closes that class going forward).

**Status:** Accepted (design locked 2026-07-15; implementation = Scheduler V2 Phase 2).

## ADR-13: Override-map keys are slot *references* resolved canonically; the lenient read is the only place allowed to prune them

**Source:** verification log 2026-07-29 (rules-engine + write-path defect sweep); [scheduler-v2-ux.md §4.1/§4.2](./scheduler-v2-ux.md).

**Context:** `DeliveryScheduleConfig.disabledSlotsJson` / `slotCapacityJson` are date-keyed maps whose inner keys are slot *values*, strings written by several generations of the editor, so a key's spelling can drift from the configured slot (`"9am - 12pm"` vs `"9AM-12PM"`). Scheduler V2 §4.2 canonicalized the booked-count matcher and the validators' *slot* lookup, but the override-map lookups themselves stayed strict (`slotCapacity[date][slotValue]`, `disabledSlots[date].includes(...)`). A drifted cap was therefore counted and rendered "Full" on the dashboard while **never being enforced at checkout**, and a drifted block never blocked; DEF-2/DEF-4 were closed for counting only. Separately: the strict WRITE gate rejects any patch referencing a slot that is not configured, and every day-override op resubmits the whole map, so one orphan key the lenient READ kept made every later day save and every slot delete fail permanently, with no in-app way to remove the orphan.

**Decision:** (1) Every override-map lookup resolves its key through `findSlotOverrideKey` ([`app/lib/slot-value.ts`](../app/lib/slot-value.ts)): canonical match, with an exact spelling winning a tie so a map holding both spellings resolves to the one the caller named. (2) `deserializeStoredScheduleRules` (the lenient read) is the ONE place allowed to drop override entries: it prunes keys naming no configured slot and collapses two keys on one date that canonicalize to the same slot (last wins, matching the counts engine), reporting each as a `ConfigHealthIssue`. The strict write gate keeps rejecting orphans outright.

**Consequence:** New enforcement code must go through `findSlotOverrideKey`, never `map[slotValue]` / `includes(slotValue)`; a raw lookup silently re-opens the counted-but-not-enforced split. Pruning belongs to the read: ops and routes must not delete override entries to work around a validation failure (`clearDayOverride` stays the only intentional per-date wipe, and a day-level block must not rewrite that date's per-slot config). Merchants see a drifted/orphaned key as a config-health banner on `/app/scheduler` instead of a dead editor. Stored shapes and column set are unchanged.

**Status:** Accepted; implemented 2026-07-29.

## ADR-14: `shopify.app.toml` (unnamed default) is DEV; PROD moved to `shopify.app.production.toml`

**Source:** verification log 2026-07-31.

**Context:** The 2026-07-13 incident (`docs/changelog.md`, `deploy-prod` SKILL.md) had a bare `npm run deploy` release to the DEV app instead of PROD because the Shopify CLI can cache the last-used `--config` selection across sessions, independent of which toml file is the unnamed default. Before this ADR, the unnamed `shopify.app.toml` held the PROD config (client_id `a9127e5f...`) and the DEV config lived at the explicitly-named `shopify.app.delivery-scheduler-dev.toml`, meaning any command run without a `--config` flag (or with a stale cached selection) defaulted toward PROD, the more dangerous direction. Two local repos under active parallel development (`live-theme-clean`, a theme repo, and this app repo) were also fighting over a shared, unscoped browser-automation profile in Claude/Playwright/DevTools tooling, prompting a broader review of this repo's default-config hygiene.

**Decision:** Swap which file is the unnamed default. `shopify.app.toml` is now the **DEV** config (was `shopify.app.delivery-scheduler-dev.toml`; client_id `51f7d1b7...`); the former default is renamed `shopify.app.production.toml` (**PROD**; client_id `a9127e5f...`, unchanged). Per-file settings (`automatically_update_urls_on_dev`, api_version, client_id, scopes) are untouched by the rename; only the filenames swapped. `npm run deploy` (bare) is disabled (prints a reminder, exits 1); `npm run deploy:dev` / `npm run deploy:prod` and `npm run dev` (now DEV by default) / `npm run dev:prod-preview` replace every ambiguous invocation in scripts and docs.

**Consequence:** A bare `shopify app dev`/`deploy`, or a stale CLI cache, now resolves to DEV, the safe direction, instead of PROD. The team updated every doc/script that referenced the old filenames (`CLAUDE.md`, `README.md`, `docs/development.md`, `docs/cloud-run-neon.md`, `docs/scheduler-v2-ux.md`, `e2e/README.md`, `.env.test.example`, `.claude/skills/deploy-prod/SKILL.md`) in the same pass. Anyone with a local `shopify app config use delivery-scheduler-dev` cached selection should re-run `shopify app config use` (or just rely on the new default); the named config `delivery-scheduler-dev` no longer resolves to a file on disk. Separately, `delivery-scheduler/.mcp.json` gained its own isolated `chrome-devtools`/`playwright` browser profiles (`${CLAUDE_PROJECT_DIR}/.browser/...`), matching the pattern already used in `live-theme-clean`, so the two repos' browser-automation tooling no longer shares a profile.

**Status:** Accepted; implemented 2026-07-31.

## ADR-15: Merchant "Edit details" rewrites the shipping address only; the overwrite carry-forward lives in one function

**Source:** merchant request 2026-08-14 ("editable order details for the customer, including address and contact number"); audited before implementation in the same session.

**Context:** The details panel was read-only except for its freeform `tagsAdd` form. The merchant needed to correct a wrong address or an unreachable phone number without leaving the app for Shopify Admin. Three properties of the Admin API shaped the answer:

1. `OrderInput.shippingAddress` **merges**, despite the schema documentation saying it "Overwrites the existing shipping address". Measured live against dev-store order `#1034` on 2026-08-14: sending `address1` alone left `firstName`, `lastName`, `city`, `provinceCode`, `countryCodeV2`, and `zip` untouched. The practical consequence is the opposite of the documented one: nothing is at risk of being erased, but **a field can only be cleared by sending an explicit `""`**; omitting the key is a silent no-op that still reports success.
2. `MailingAddressInput` accepts `provinceCode` and `countryCode` only; there is no free-text `province`/`country` (the example in Shopify's own `orderUpdate` docs is stale on this). The read side spells the country `countryCodeV2`, the write side `countryCode`.
3. The customer's own phone (`customer.defaultPhoneNumber`, shown as "Sender phone") lives on the **customer record**, not the order. Changing it needs `write_customers`, which the app does not hold — and adding a scope forces a merchant reinstall.

**Decision:** Ship a single-order `editDetails` op + panel modal covering **four fields only**: `address1`, `address2`, `city`, and the **receiver** phone (`shippingAddress.phone`, the number the rider actually calls). Recipient name, company, province, and country are **carried forward, not editable**; `buildNextShippingAddress()` in [update-order-contact.server.ts](../app/services/update-order-contact.server.ts) is the only place that carry-forward happens, and nothing else in the codebase builds a `MailingAddressInput` for an order. Given the measured merge behaviour the carry-forward is belt-and-braces rather than load-bearing, and the team kept it on purpose: the *documented* contract is "overwrite", so if Shopify ever makes the behaviour match the docs, this keeps working. The stored address is **re-read server-side** at write time and never taken from the client, so the carry-forward values cannot be steered by a crafted form post. Sender phone stays read-only; the merchant declined it rather than pay a reinstall for a field the rider does not dial.

**The clear-a-field rules, all measured on `#1034`:** `address2: ""` and `phone: ""` clear those fields; an omitted key does not. **`zip: ""` is rejected** ("Enter a postal code"; PH requires one) and the rejection **fails the entire mutation**, so a merchant clearing the ZIP would also lose the street and city edits submitted alongside it.

**The ZIP was therefore dropped from the form entirely (merchant call, 2026-08-14).** It shipped first as an editable field guarded against clearing; the merchant's read was that it slowed the form down for a field that can't be cleared and is rarely what's wrong. It is now a **carry-forward** field like the recipient name — re-sent from the stored address, shown read-only in the modal's "Kept as is" line, and unreachable from the form (`OrderContactPatch` has no `zip`, and a test asserts a smuggled `zip` key on the patch object cannot reach the input). That deleted the guard, the inline error, and a whole class of failure along with it.

Per the merchant's call, the op is an **administrative override in the ADR-10 sense**: it is never blocked, but the modal warns on the two cases where the edit does less than it looks like it does — a FULFILLED/in-transit order (the parcel is already out) and a changed city (shipping was priced by the courier at checkout and is not re-computed).

**Consequence:** `/app/orders` gains a **fifth order write path**, and the first one that mutates customer-facing data. It is **not** a delivery write path: it touches no delivery metafield, tag, or customAttribute, so the api.md §2 table is unchanged. The orders loader query grew five read-only fields (`firstName`, `lastName`, `company`, `provinceCode`, `countryCodeV2`) so the overwrite has something to carry forward. Two known limits accepted as-is: no concurrency guard (last write wins, same posture as REC-5 on the reschedule path), and the delivery fee is not re-priced on a city change (surfaced as a warning instead).

**Status:** Accepted; implemented and **live-smoked 2026-08-14** on `fix/scheduler-rules-sweep`. The smoke ran against dev-store order `#1034` (snapshot → six mutations → full restore, verified field-by-field) and **found a real bug**: the first implementation cleared a field by omitting its key, which under the actual merge semantics is a silent no-op that still reports success. The team fixed it by sending an explicit `""` for the clearable editable fields and blocking the un-clearable ZIP up front. 29 unit cases now pin the measured behaviour, including one asserting the exact input Shopify accepted on `#1034`.

## ADR-16: Listen to Lalamove's Open API webhook to auto-mark fulfillments "Delivered"; this does NOT reopen ADR-1

**Source:** merchant request 2026-08-15/16 ("pag na-deliver na sa Lalamove, dapat automatic mag-mark as delivered ang Shopify order"); spiked live against the production Lalamove Open API before implementation in the same session.

**Context:** A fulfilled order never flips to "Delivered" in Shopify — Shopify has no visibility into the courier's actual drop-off, so a human has to click Shopify's own native "Mark as delivered" button by hand once the merchant's Lalamove tracking link shows it arrived. The merchant books every Lalamove delivery manually on `web.lalamove.com` (the general "Place Order" flow, not the Shopify-integrated "Shopify Orders" tab), so there is no Shopify-side hook at booking time.

Two things were verified live against the production Lalamove Open API before committing to a design:

1. **The merchant-facing tracking share link (`share.lalamove.com/?<token>&...`) does NOT carry Lalamove's real order id.** `getOrderStatus` 404s on that token. The real numeric order id is the "`#<id>`" shown in the Lalamove web Records list; `getOrderStatus` on THAT id returns full order data, including a `shareLink` field containing the same kind of opaque share token, confirming the two are unrelated identifier spaces.
2. **There is no "list orders" endpoint** in the Open API (confirmed against the live API reference); only get/create/edit/cancel-by-id, driver lookups, priority-fee, and webhook config. A poller can therefore only check ids it already knows about; it cannot discover orders on its own.

The Open API does, however, expose an `ORDER_CREATED` webhook event, and it fires for an order regardless of whether it was booked via the API or the general web portal (same account, same visibility), confirmed by successfully calling `getOrderStatus` on a web-portal-booked order using the merchant's Partner Portal API key.

**Decision:** Add a webhook-driven status listener (`app/routes/webhooks.lalamove-tracking.ts`), NOT a dispatch integration:

- **(Superseded design, kept for the record below the addendum)** ~~`ORDER_CREATED` → fetch the order's drop-off phone via `getOrderStatus`, phone-match against recent fulfilled Shopify orders~~. **Abandoned same-day; see the "Polling-only" addendum.**
- `ORDER_STATUS_CHANGED` with status `COMPLETE`/`COMPLETED` → look up a tracked row and call `fulfillmentEventCreate(status: DELIVERED)` on the stored fulfillment id. Kept wired as best-effort only (see addendum; this never actually fires for this merchant's orders).
- A fallback poller (`app/routes/internal.lalamove-poll.ts`), triggered by a Google Cloud Scheduler job (`delivery-scheduler-lalamove-poll`, every 10 minutes, cut down from 30 the same day after a live gap, see addendum). **This is the mechanism that actually runs in practice**, not a fallback for a working webhook (see addendum).

This deliberately does **not** touch dispatch: the merchant keeps booking every delivery by hand exactly as before; no order-creation, edit, or cancel call is ever made against the Lalamove API; the `markFulfilled` tracking-URL field's existing behavior is untouched.

**Why this doesn't reopen ADR-1:** ADR-1 removed a **dispatch** integration: code that booked/cancelled Lalamove deliveries and wrote `lalamove.*` metafields as a competing courier-management surface. This is a **read-only status listener** with no dispatch surface, no `lalamove.*` metafield (the correlation lives in a Postgres side-table, never on the order), and no UI. A future agent reading ADR-1's "do not reintroduce custom Lalamove code" must read this ADR first: that guidance is about dispatch, not about listening for a courier's own completion signal.

**Consequence:**
- New Prisma model `LalamoveTracking` (migration `20260816000000_add_lalamove_tracking`, hand-written rather than `prisma migrate dev`; see `docs/known-issues.md` on the shadow-DB trap).
- New env vars: `LALAMOVE_API_KEY`, `LALAMOVE_API_SECRET`, `LALAMOVE_MARKET` (`PH`), `LALAMOVE_ENV` (`sandbox`/`production`), `LALAMOVE_SHOP` (single-shop app; since 2026-09-08 `SHOP_DOMAIN` is the shared name and `LALAMOVE_SHOP` remains a fallback, see ADR-25), `LALAMOVE_POLL_SECRET`.

**Status:** Accepted; deployed to production 2026-08-16 (Cloud Run revision `delivery-scheduler-00228-22m`). See the addendum immediately below for the as-shipped design, which differs from the webhook-based design above.

### ADR-16 addendum (same day, 2026-08-16): Webhook path abandoned; polling-only, explicit Order ID entry

**What changed:** the phone-matching/webhook-driven design above was designed, built, deployed, AND then disproven by a live test — all in the same session, before any merchant relied on it. Keeping the original text above (struck through) rather than rewriting history, because the reasoning trail is the point of an ADR.

**What the live test showed:** with the real production Lalamove webhook registered and a merchant test delivery in progress (a real driver assigned, then cancelled), the Lalamove Partner Portal's own **"Webhook attempts" log recorded ZERO order-related events**: no `ORDER_STATUS_CHANGED`, no `DRIVER_ASSIGNED`, while an unrelated `WALLET_BALANCE_CHANGED` event delivered successfully on the exact same URL/credentials in the same window. Direct `getOrderStatus(orderId)` reads, by contrast, succeeded for that same order (both while `ON_GOING` and after `CANCELED`). Conclusion: Lalamove's push webhooks are tied to orders **placed via the API**. The docs say this explicitly only for `ORDER_CREATED`, but the observed behavior shows it holds for the other event types too, at least for this account. Reads work account-wide; pushes don't. This is a Lalamove platform characteristic, not a misconfiguration; there is nothing on our side or in the Lalamove Partner Portal UI that changes it.

**Revised decision:** the correlation step is now **explicit, not inferred**. The merchant pastes the real Lalamove Order ID, found in the Lalamove app's order detail **"Additional info"** section (a plain numeric id, e.g. `3562752825958289729`; NOT the `share.lalamove.com` tracking link), into a new optional field in the existing "Mark as fulfilled" modal, alongside the tracking number/URL already collected there. Single-order only (a bulk fulfillment of >1 order does not show the field; one courier id cannot correlate to many orders). `recordLalamoveOrderId()` (`lalamove-tracking.server.ts`) validates the id via `getOrderStatus` before storing the `LalamoveTracking` row (the route catches a mistyped id, e.g. the share-link token pasted by mistake, immediately rather than silently tracking nothing), and immediately marks the order Delivered if the courier already completed by the time the id is pasted.

The webhook route (`webhooks.lalamove-tracking.ts`) stays wired; it costs nothing to keep and might someday receive something. But the team deleted the `ORDER_CREATED` handling and the phone-matching machinery (`matchAndRecordLalamoveOrder`, `normalizePhoneForMatch`, `findUndeliveredFulfilledOrderByPhone`) from `lalamove-tracking.server.ts` entirely, along with their unit tests, rather than leaving them as dead code. The `internal.lalamove-poll.ts` fallback poller is unchanged in implementation but is now the **primary** mechanism, not a safety net for a working webhook. It is wired to a Google Cloud Scheduler job (`delivery-scheduler-lalamove-poll`, every 30 minutes, HTTP POST with the `x-lalamove-poll-secret` header) created the same day.

## ADR-18: Sidekick app extensions: read-only data tools + deep-link actions (no write surface)

**Deploy-validation addendum (2026-08-19, same day):** dalawang constraint ang lumitaw sa unang `npm run deploy:dev` na hindi nahuli ng `shopify app build`: (1) ang `admin_link` extension ay tumatanggap lang ng ISANG `[[extensions.targeting]]` block — kaya ang scheduler-date intent ay hiniwalay sa sariling extension `delivery-sidekick-scheduler` (kabuuang extensions: 10); (2) ang `[sidekick] extensions_summary` ay may 500-CHARACTER cap sa CLI validation (hindi "256 tokens" gaya ng docs) — pinaikli. **Live smoke (dev store, parehong araw):** pumasa ang server-side intent validation para sa `application/shipment`; ang `get_delivery_booked_counts` at `get_order_delivery` tools ay tinawag ni Sidekick nang matagumpay end-to-end (may one-time "Allow Sidekick to access your Delivery Scheduler app data?" consent ang unang paggamit); parehong deep link gumana (`?date=` day panel bukas, `?order=` panel bukas — kasama ang legacyId-lookup-first workflow mula sa instructions.md). Ang OPTIONS preflight ay sinasagot ng 204+CORS bago pa ang RR7 (ang H-1 risk ay hindi nag-materialize sa dev). ISANG live issue: sa bawat successful navigation, nag-uulat si Sidekick ng "there was an issue opening" — ang deferred `describe_open_*` stub ang sanhi; mitigation na na-deploy (v25): explicit "do not call / never report failure" guidance sa instructions.md + tool descriptions ng parehong action extension. Ang tunay na ayos (App Home handler wiring) ay nakalista pa rin sa known-issues.

**Source:** Extensions Modernization Feature E, implemented 2026-08-19 on `feat/extensions-modernization`. Upstream contracts: [Build app data for Sidekick](https://shopify.dev/docs/apps/build/sidekick/build-app-data) and [Build app actions for Sidekick](https://shopify.dev/docs/apps/build/sidekick/build-app-actions).

**Context:** Sidekick can only answer delivery questions if this app tells it. Delivery date, time slot, per-date capacity, blocked dates/slots, the same-day cutoff and an order's reschedule state live nowhere Sidekick can already see — the config is in `DeliveryScheduleConfig` (Postgres) and the per-order state is in metafields/tags Sidekick does not read. Without an extension, Sidekick either says "I don't know" or invents an answer from order tags.

**Decision — the FULL pair, but with a hard read-only posture:**

- **App Data (`delivery-sidekick-data`, `admin.app.tools.data`)** registers **three** tools, deliberately split by question shape rather than one generic `search`: `get_delivery_booked_counts` (capacity — "is Friday full?"), `get_order_delivery` (one order — "when is #4111 going out?"), `get_schedule_config_summary` (settings — "what's our cutoff?"). Splitting them is what makes Sidekick pick correctly (the tool *description* is the routing signal) and lets the cheap question stay cheap: only `get_delivery_booked_counts` pays the live Admin order scan (ADR-12), while `get_schedule_config_summary` is a Postgres read and `get_order_delivery` is one GraphQL query for one order.
- **Backend (`app/routes/sidekick.tools.*.ts` + `app/services/sidekick-tools.server.ts`)** is **READ-ONLY and stays that way**: zero mutations, zero delivery-state writes, zero Prisma writes. The api.md §2 write-path contract is untouched — Sidekick adds a *reader*, not a fifth write path. `test/sidekick-tools.test.ts` enforces it two ways: the mocked `admin.graphql` is asserted never to receive a mutation string, and the route/service sources are grepped for mutation and write-helper names.
- **App Actions (`delivery-sidekick-actions`, `admin.app.intent.link` ×2)** are **navigation only**. Writing a delivery from Sidekick would have meant a new write path with no merchant confirmation step; instead each intent deep-links to the page that already owns the write — `/app/orders?order=…&search=…` (the panel's existing merchant `reschedule` op, ADR-10) and `/app/scheduler?date=…` (the existing scheduler day-override ops). Both URL params already existed as URL state; the only app-side change was normalising a full order GID passed to `?order=` down to its numeric tail.
- **Auth is a new CALLER, not a new mechanism.** The Sidekick sandbox sends the same session-token `Authorization` header as the embedded admin iframe, so `authenticate.admin(request)` handles it via token exchange — these routes simply join the nine route files already calling it. The one difference from an embedded route, and the reason they are worth listing separately: the sandbox is **cross-origin**, so every response goes through the `cors` helper `authenticate.admin` returns. These are the first and only routes in the app that need it.
- **The auth call itself is guarded (`authenticateSidekickRequest`).** `authenticate.admin` legitimately *throws a `Response`* for the platform's own auth flow — rethrown untouched, since swallowing it would break embedded auth. But it also touches Prisma session storage behind Neon, and a cold-start timeout there throws a plain `Error` that React Router renders as a 500 — which Cloudflare then replaces with its HTML page, reproducing the exact ADR-11 failure this whole contract exists to avoid. A non-`Response` throw therefore returns `200 + {ok:false}` like every other failure, with the CORS headers written by hand because the `cors` helper is part of the value the failed call never returned.
- **Response contract: ADR-11 applies unchanged.** Every upstream failure and every invalid input answers `200 + {ok:false, error}` with a message written for Sidekick to relay. A 5xx would be replaced by Cloudflare's HTML page and break the sandbox fetch exactly as it broke the embedded fetcher in 2026-07.
- **A failed scan reports "unknown", never a number.** When `countsMeta.status` is `error` or `skipped` the live scan produced nothing, and the `booked` values still on the rules object are stale config leftovers (typically 0). Emitting them would let Sidekick tell the merchant "10 of 10 free" on a fully booked day during an Admin outage, so `booked`/`remaining`/`full` come back **null** on those statuses while `capacity` (real config) is kept. Similarly, an explicitly requested date with no capacity configured is reported in `untrackedRequestedDates` rather than as an empty result, because "not capacity-limited" and "nothing booked yet" are different answers.
- **Response size is a first-class constraint.** Sidekick rejects tool responses over 4,000 tokens, so every list is capped and reports what it dropped (14 dates, 12 slots/date, 20 slots and 10-item samples, exactly one order) instead of truncating silently. `countsMeta.status` is surfaced verbatim as `countsStatus` plus a plain-language `countsNote` so a `partial` scan can never be presented as a complete number.

**Constraints discovered and accepted:**

- **Intent `type` is a fixed Shopify enum** — custom types are rejected at deploy (`Intent is invalid: type '<value>' is not supported`). There is no delivery/scheduling type. `shopify/order` exists but only supports `import` / `import+bulk`, the wrong verb. Both intents therefore declare **`application/shipment`**, the closest supported fit for a scheduled delivery: `edit` for "change when this order is delivered", `create` for "set up delivery capacity for this date". A better type should be proposed upstream at [Shopify/app-intent-types](https://github.com/Shopify/app-intent-types).
- Both values map with `mapTo: "query_param"` (not `param`) because the destinations carry query params, not `{placeholder}` path segments.
- **Intents are only registered if the extension declares at least one tool**, and for an `admin_link` extension the tool handler must be registered by the React component at the destination URL — not by the extension. `tools.json` therefore declares one optional, read-only `describe_open_delivery_view` tool; **its handler is deliberately NOT wired into App Home yet.** Deep-link navigation works regardless. Accepted risk: if Sidekick calls that tool, the call does not resolve — the merchant is already on the correct page by then. `instructions.md` steers Sidekick to treat navigation as the action.
- **`api_version` outcome: bumped to `2026-04`** (from the scaffold's `2025-10`) with `@shopify/ui-extensions` at `2026.4.x`, matching all seven pre-existing extensions. Verified: `@shopify/ui-extensions@2026.4.4` ships `build/ts/surfaces/admin/targets/admin.app.tools.data.d.ts`, and `shopify app build` succeeds and regenerates `shopify.d.ts` from `tools.json`. The `admin_link` actions extension carries **no** `api_version` key (that type does not take one).

**Consequence:** extension count 7 → **9**; a new caller of `authenticate.admin` — not a new mechanism, but the **first cross-origin one** (hence `cors`); one new service module and one new test file. Sidekick's answers inherit ADR-12's accepted ≤60s booked-count staleness.

`shopify.app.toml` (**DEV only**) gains a `[sidekick]` `extensions_summary`. **`shopify.app.production.toml` is deliberately untouched and must receive the same `[sidekick]` block at the next gated prod deploy (ADR-14)** — recorded here so a prod release is never left half-configured silently: extensions would ship without the summary that tells Sidekick what this app is for.

**Status:** Implemented on `feat/extensions-modernization`, unit-tested and CLI-build-validated locally. **NOT yet deployed** — intent `type`/`action` validation happens server-side at `shopify app deploy`, and Sidekick behaviour can only be exercised against a deployed app version. Deploy is a merchant-go gate.

## ADR-19 — Occasion reminder emails: fully automatic yearly retention sends, zero order writes

**Date:** 2026-08-21 · **Status:** ~~Implemented + deployed~~ **REVERTED / REMOVED 2026-08-28** — the feature ran in production but detected nothing (see the Reverted note at the end of this ADR); the merchant moved to a dedicated third-party Shopify reminder app and the whole feature was deleted from the codebase. Retained here as historical record.

**Context:** Anniversary and birthday flower buyers re-order yearly, but nothing reminded them. The infra was already 90% built: SMTP sender (`sendCustomerEmail`, ADR-11/E-6), `EmailSendLog`, order delivery dates on metafields, and the Cloud Scheduler → shared-secret internal route pattern (ADR-16 poller). Research (2026-08-20) put occasion reminders as the highest-value retention lever for this store.

**Merchant decisions (2026-08-20/21):** fully automatic (no review queue); TWO touches — 7 and 3 days before the occasion (`TOUCH_OFFSETS`, code constants); ALL orders enter the calendar (occasion keyword detection only personalizes copy, never gates); recurring EVERY year until unsubscribe; email wording is the merchant's own template verbatim (Drive: `flowercart-reminder-email-sequence.md`, mirrored into the repo's brand-voice context) with fallback words for missing data ("your special day" / "someone special"); greeting name = billing first, fallback shipping; recipient name = the order's shipping/delivery name — NEVER parsed from the card message (~70% parse failure, merchant-measured); the 3-day email carries `ANNIV200` (₱200 off) and is SKIPPED when the customer has re-ordered since the 7-day send.

**Decision — mechanics:**

- **Yearly recurrence via roll-forward:** the nightly scan's Shopify search only ever looks ONE year back (`created_at:`-range + client-side `custom.date`/`deliveredAt` filter — NOT `metafields.custom.date:` search, which the orders query silently ignores, verified 2026-07-11). Older years roll forward from the app's own SENT `OccasionReminder` rows, so search cost never grows with age. A fresh re-order (Source A) beats the old chain (Source B) in a per-(email, month-day±2d) dedupe.
- **Zero order writes, machine-enforced:** read-only orders searches only; writes are Postgres rows (`OccasionReminder` unique on shop+order+year+touch; `ReminderSuppression`; `ReminderConfig`) plus the same `EmailSendLog` audit row as the sendEmail op. The §2 contract is untouched; `test/occasion-reminders.test.ts` clones the ADR-18 read-only grep guard over all six reminder sources.
- **Safety without human review:** suppression checked at scan AND send time (an unsubscribe after the 7d email kills the 3d email and cuts the whole yearly chain); Shopify `defaultEmailAddress.marketingState UNSUBSCRIBED` is a hard skip at entry; sends are HELD when the unsubscribe secret/app URL is missing (never an email without a working opt-out); `MAX_SENDS_PER_RUN=50` protects the Namecheap mailbox; 3 attempts then FAILED; merchant kill switch (`ReminderConfig.enabled`, default false) + per-row Suppress on `/app/reminders`.
- **Unsubscribe:** HMAC-signed tokens (`REMINDER_UNSUBSCRIBE_SECRET`), `GET /public/reminder-unsubscribe`, generic 200 page for valid AND invalid tokens (no enumeration oracle), no expiry.

## ADR-20 — Multi-channel agent architecture: transport-free core + customer-account chat as the second channel

> **Superseded by [ADR-25](#adr-25--meta-business-agent-owns-the-chat-this-app-exposes-an-agent-api-the-in-repo-messenger-bot-support-chat-and-storefront-widget-are-removed) (2026-09-08).** The agent core, Messenger adapter, and support-chat extension described below were removed from the codebase. Kept as history; nothing in this ADR describes running code.

**Date:** 2026-08-21 · **Status:** Implemented on `feat/extensions-modernization`; typecheck + full suite green (846/846). **NOT deployed** — nothing in this ADR has run against a real store. See the 2026-08-21 entry in [verification-log.md](./verification-log.md) for the exact gap.

**Context:** The FlowerCart Messenger agent's brain — the LLM tool loop with the prompt-cache split, the 5-iteration ceiling, and the carousel/summary/add-on suppression rules — lived entirely inside `messenger-agent.server.ts`, welded to Meta's primitives (quick replies, generic template carousel, 2000-char cap). The merchant wants the same assistant reachable from a signed-in customer's account page, where Messenger's affordances don't exist and markdown/React cards do.

**Decision — extract a transport-free agent core:**

- `app/services/agent-channel.ts` (types only, zero I/O, zero npm deps, no `.server` import) defines the neutral contract: `AgentChannel` (kind/identity/capability-flags/threadId) in, `AgentReply` of neutral `AgentBlock`s (`text` / `products` / `slots` / `order` / `choices` / `summary`) out. Three frozen capability presets (`MESSENGER_CAPABILITIES`, `CUSTOMER_ACCOUNT_CAPABILITIES`, `STOREFRONT_CAPABILITIES`) tell the brain what a transport can render instead of the loop asking "am I on Messenger?" anywhere inside itself.
- **`ordering` is a capability, not a render flag** (added 2026-08-21 after review). `ChannelCapabilities.ordering` is `true` ONLY in `MESSENGER_CAPABILITIES`; both web presets are `false`, per the merchant's v1 decision that the web channels are **read-only support** — ordering stays Messenger-only. Two hard reasons, not just policy: (1) order state is keyed by `MessengerThread.psid`, and a web `threadId` is a Shopify customer GID with no `MessengerThread` row, so every `update_order` call on a web channel would die at the Prisma lookup; (2) the deterministic `CONFIRM_ORDER_<key>` interception (the Commitment rule: no draft order without an explicit tap) lives only in the Messenger adapter, so a Confirm affordance on the web would send its payload to the LLM as ordinary text and commit nothing. Enforcement is layered: `runAgentTurn` includes the order-mutating `update_order` tool only when `messengerOrdersEnabled() && channel.supports.ordering` (and passes the same AND into `buildStaticSystemPrompt`, so a read-only channel's prompt says it cannot take orders); it drops any `summary` block on a non-ordering channel (logging kind only, never text); the support-chat worker short-circuits a `CONFIRM_ORDER_`/`EDIT_ORDER` message BEFORE the LLM with a fixed "ordering is not available in this chat" reply; and the customer-account extension renders a `summary` block as plain text with no Confirm button.
- `app/services/agent-core.server.ts` exports `runAgentTurn()` — the loop itself, lifted VERBATIM out of `messenger-agent.server.ts` and re-expressed in the neutral vocabulary. It does no Prisma reads, no Meta sends, no `repliedAt` bookkeeping, no `humanControl` gate — those stay the CALLER's job so the zero-duplicate guarantee stays owned by whoever owns the transport, instead of quietly duplicating per channel.
- `messenger-agent.server.ts` is now the FIRST **adapter**: `processAgentTurnByMid` keeps all its Messenger-specific bookkeeping and calls `runAgentTurn()` for the LLM part, translating the returned blocks back into quick replies / carousel. This is a live rewire, not a parallel path — a change inside `agent-core.server.ts` moves production Messenger behavior, so both `test/agent-core.server.test.ts` and `test/messenger-agent.server.test.ts` cover it.

**Decision — customer accounts as the second channel, not the storefront or a standalone widget:**

- **Authenticated identity for free.** `authenticate.public.customerAccount` hands back a verified `sub` claim (the customer GID) — no login flow to build, no guessing which of several unauthenticated visitors is asking about which order.
- **Zero-question order lookup.** A signed-in customer's own orders can be listed with no extra verification (`lookupOrdersByCustomerId` in `order-lookup.server.ts`) — the caller's auth already proved identity, unlike the anonymous Messenger channel.
- **Smaller blast radius.** A storefront-wide chat widget is reachable by anyone, including bots and competitors probing the assistant; a customer-account page is reachable only by an authenticated customer with a real account, and it is not yet linked into the checkout/account editor at all (see Status).

**Decision — enqueue-then-poll, not SSE:**

- Customer-account UI extensions run inside a **sandboxed Web Worker with no documented streaming support** and a buffered `fetch` — there is no supported way to keep a connection open and stream tokens back.
- **Cloud Run throttles CPU once a response returns** — the same constraint that already forced the Messenger webhook onto Cloud Tasks (ADR pre-dating this doc's numbering; see the Messenger phase-3 section of [api.md](./api.md)) applies here too: an agent turn (3-15s) cannot run inside a held-open request.
- So `POST /api/support-chat` records the turn, mints a `SupportChatJob` row, enqueues a Cloud Tasks task, and answers in under a second; `GET /api/support-chat/:jobId` is polled by the extension until `status` flips to `"done"` or `"failed"`. The worker (`webhooks.support-chat_.worker.ts`) reuses the Messenger worker's exact HMAC scheme and secret (`MESSENGER_WORKER_SECRET`) — one shared queue-auth mechanism, two job kinds — and the same zero-duplicate posture: a job whose status has left `"pending"` is already finished, so a Cloud Tasks retry after success is a no-op.

**Decision — order lookup: order-number + zip with an attempt limit (replaces email-only for the anonymous Messenger path):**

- The prior `lookupOrdersByEmail` tool trusted a bare email string typed into Messenger — a real name/email guess was enough to pull someone else's order status. `order-lookup.server.ts` adds `lookupOrderByNameAndZip`: the customer supplies BOTH the order number and the checkout zip (both are on the order confirmation email, so no harder for a legitimate customer), the zip comparison happens IN CODE against `shippingAddress.zip` — never inside the Shopify search query string — and every failure path (wrong order#, wrong zip, no shipping address on file) returns the byte-identical generic failure string, so a guesser learns nothing about which half they got right.
- **Attempt limit (superseded — see addendum below):** the guard originally lived on `MessengerThread.lookupFailures`/`lookupLockedAt` (migration `20260821000000_add_lookup_attempt_limit`), gated on `context.psid` inside `messenger-agent-tools.server.ts`.
- `lookupOrdersByCustomerId` is the parallel, unthrottled function for a surface that already has verified identity (the new customer-account channel) — no order-number/zip challenge needed there, because the auth itself is the verification.
- `lookupOrdersByEmail` (in `messenger-orders.server.ts`) is left in place, unused by the new tool wiring, rather than deleted in this pass.

**Addendum (2026-08-21, review fix) — the lockout was Messenger-only by construction; made channel-agnostic:**

- **What was wrong:** `context.psid` is a Messenger-only field — `agent-core.server.ts`'s default tool context is `{ threadId: channel.threadId }`, which never sets `psid`. So on the customer-account/storefront channels, both the `isLookupLocked`/`recordLookupFailure` calls in `messenger-agent-tools.server.ts` were skipped outright (`if (context.psid && ...)`), and even if that guard had been widened to `context.threadId`, the storage itself (`MessengerThread`, keyed by `psid`) has no row for a web `threadId` (a customer GID), so a write there would silently no-op. Net effect: the anti-guessing brute-force guard was entirely absent on the web surface.
- **Fix:** a new channel-agnostic `LookupAttempt` model (migration `20260821020000_add_lookup_attempt`), keyed by the resolved thread key (`key String @id`, `failures`, `lockedAt`), replaces `MessengerThread.lookupFailures`/`lookupLockedAt` as what `order-lookup.server.ts`'s `isLookupLocked`/`recordLookupFailure`/`clearLookupFailures` actually read and write. `messenger-agent-tools.server.ts` resolves the key ONCE per call as `context.threadId ?? context.psid` and uses that single value for both the lookup and the lockout; if neither is present it returns a designed `{ ok:false }` instead of silently skipping the guard. The old `MessengerThread` columns are left in place (dropping columns is destructive) but are no longer read or written — marked SUPERSEDED in `schema.prisma`.
- **Also fixed in the same pass:** (1) the lock used to never reset once a customer crossed the threshold — a single further mistake made *after* the 30-minute window had already expired re-locked them for another 30 minutes, forever, because only a success cleared the counter; `recordLookupFailure` now resets the count to 0 before counting a new attempt once the window has expired. (2) `ORDER_LOOKUP_QUERY` fetched only `first: 5` unsorted nodes, so a short order number that is a `name:` search prefix of longer ones (e.g. `#100` vs `#1000`..`#1004`) could fall outside the page and burn a lockout attempt on a false negative; the query now fetches `first: 25` with `sortKey: RELEVANCE`, and a full page with no exact match is returned as `{ ok:false, ambiguous:true }` — an inconclusive search, not a wrong-guess — which `messenger-agent-tools.server.ts` explicitly excludes from the failure count.

**Consequence:** Postgres model count 8 → 12 (`SupportChatThread`/`SupportChatMessage`/`SupportChatJob`, migration `20260821010000_add_support_chat`; `LookupAttempt`, migration `20260821020000_add_lookup_attempt`, per the addendum above) + the now-superseded `MessengerThread` lookup-guard columns left in place; extension count 10 → 11 (`extensions/support-chat`, full-page `customer-account.page.render` target — Shopify requires a full-page target to be the only target in its extension, hence its own directory); a NEW auth surface (`authenticate.public.customerAccount`, distinct from both `authenticate.admin` and the hand-rolled `jwtVerify` used by the older `public.customer-account.*` reschedule routes) alongside the existing six; zero Shopify order writes anywhere in this ADR — everything lands in the three new Postgres models only, so the [api.md §2 write-path contract](./api.md#2-actual-order-write-paths-the-only-places-that-mutate-delivery-state) is untouched.

**Two required manual steps before this can go live, neither done yet:**

1. Partner Dashboard → app → Configuration → "Allow network access in checkout and account UI extensions" — without it, `network_access = true` in the extension's `shopify.extension.toml` has no effect and every `fetch()` from the extension is blocked.
2. After deploy, the "Support chat" page block has to be added manually in Settings → Checkout and accounts → Customize — deploying the extension does not place it anywhere by itself.

Both are called out in `extensions/support-chat/README.md` and repeated in [verification-log.md](./verification-log.md) so the gap is not silently assumed closed by a future reader.

## ADR-21 — Storefront chat widget: third channel (theme app embed), App Proxy signature as the anonymity trade-off ADR-20 deferred

> **Superseded by [ADR-25](#adr-25--meta-business-agent-owns-the-chat-this-app-exposes-an-agent-api-the-in-repo-messenger-bot-support-chat-and-storefront-widget-are-removed) (2026-09-08).** The chat widget, its routes, and `WidgetConfig` were removed. The theme extension survives only as `delivery-fee-checker` (same uid) for the fee-checker block. Kept as history.

**Date:** 2026-08-22 · **Status:** Implemented AND deployed to production on the same day (merchant go: "gawin mo yan end to end... kailangan lumabas sa live theme ng maayos"). Live on `flowercart.store`'s active theme (`VERIFY-dynamic-cta`), app embed toggle ON, real turns verified against the production backend both via hand-signed curl and via the browser. 952/952 tests, typecheck clean.

**Context:** ADR-20 explicitly deferred a storefront-wide widget, citing "reachable by anyone, including bots and competitors probing the assistant" as the reason customer-account chat shipped as the second channel instead. The merchant's actual ask, once clarified, was exactly that deferred surface: a floating chat bubble, bottom-right, on any storefront page, NOT gated behind customer login — reference shown was bouqs.com/orders/status's floating widget. `agent-channel.ts` already had `STOREFRONT_CAPABILITIES` and the `{type:"anonymous", conversationId}` identity shape sitting unused since ADR-20 — this ADR wires that scaffolding to a real route and a new extension type rather than inventing new abstractions.

**Decision — a Theme App Extension (app embed), not a second customer-account page:** Customer Account UI Extensions render only within an assigned page/block inside the authenticated account area — there is no floating-overlay render mode, so the existing `extensions/support-chat` mechanism cannot be repurposed for a public, anonymous, page-flexible bubble. `extensions/storefront-chat-widget` (`type = "theme"`, `target: "body"` app embed, scaffolded via `shopify app generate extension -t theme_app_extension` rather than hand-authored) is the first Theme App Extension in this repo. An app embed gives one native, Shopify-managed global on/off toggle (Theme Editor → App embeds) — the closest fit to "ideploy sa ibat ibang page pag gusto ko"; a `page_visibility` Liquid setting (comma list of `request.page_type`/`page.handle` values, evaluated server-side in the block itself before anything renders) adds per-page restriction on top, since app embeds are otherwise site-wide-or-nothing.

**Decision — reuse the agent-core; `runSupportChatTurn` reads channel off the thread row, not a threaded parameter:** `SupportChatThread` gained a `channel` column (`"customer-account"` default, `"storefront"` for the new anonymous threads, migration `20260822010000_add_support_chat_channel`). `runSupportChatTurn` looks this up once and branches to the right `AgentChannel` shape, instead of accepting a channel argument that every caller (worker route, both inline-dev fallbacks) would have to construct identically. This is the same drift class ADR-20's own addendum already had to fix once for the lockout key (`context.psid` vs `context.threadId`) — reading a single source of truth off the persisted row, rather than trusting N call sites to agree, closes that class of bug before it can recur. Consequence: `webhooks.support-chat_.worker.ts` needed **zero code changes** to serve the new channel.

**Decision — anonymous identity via `"storefront:" + conversationId`, not a bare UUID:** `ensureAnonymousSupportChatThread` mints `id: "storefront:" + conversationId`, `customerGid: null`. The prefix is cheap defense-in-depth namespacing against the id space ever overlapping a customer GID string; `conversationId` itself is client-minted (`crypto.randomUUID()`, persisted in `localStorage`) and 100% unauthenticated — nothing about it proves identity, unlike the customer-account channel's JWT-verified `sub` claim.

**Decision — App Proxy signature-gating + dual rate limits answer ADR-20's "reachable by anyone" objection, rather than re-litigating whether to build it:**

1. **App Proxy signature (`verifyAppProxySignature`, hand-rolled HMAC-SHA256 over sorted query params keyed by `SHOPIFY_API_SECRET`, same helper `apps.schedule-rules.products.ts` already uses) is the only auth.** A prober still has to load the real storefront page and drive the real widget JS to get a Shopify-signed request — same exposure as any other public page, not an arbitrary open internet POST.
2. **New `AgentRateLimit` model** (migration `20260822000000_add_agent_rate_limit`, fixed-window counter — window-expiry-reset bug written correctly from the start this time, per the `recordLookupFailure` lesson cited in ADR-20) backs two layers checked BEFORE any `SupportChat*` write: per-`conversationId` (20 turns/60min) and per-IP from `X-Forwarded-For` (60 turns/60min, backstop for the fact that `conversationId` is client-controlled and `localStorage.clear()`-resettable). Nothing today throttles turn volume on Messenger or customer-account either — this is net-new protection, not a downgrade.
3. **`STOREFRONT_CAPABILITIES.ordering` stays `false`**, same posture as the customer-account channel — worst case a prober extracts is read-only catalog/delivery/order-status info, and order lookup still carries the existing `LookupAttempt` anti-guessing lockout.

**Status-code convention deliberately diverges from ADR-11 here, same as the customer-account routes' rationale did NOT apply to `apps.schedule-rules.products.ts`:** ADR-11 ("always 200, never a thrown 5xx") exists because a customer-account extension's sandboxed `fetch` sees Cloudflare replace an origin 5xx body with generic HTML. App Proxy is a server-to-server Shopify-edge proxy with no such problem — `apps.schedule-rules.support-chat.ts` and its poll route use real HTTP status codes (401/400/429/200/502) throughout.

**Two new App Proxy routes, both under the app's one registered proxy prefix (`/apps/schedule-rules`, `shopify.app.production.toml` only — the DEV app config has no `[app_proxy]` block at all, so this feature is unreachable from the DEV app by construction, not by oversight):**

- `POST /apps/schedule-rules/support-chat` — validates `conversationId` (UUID pattern) and `message` (≤4000 chars, `STOREFRONT_CAPABILITIES.textLimit`), checks both rate-limit layers, then `ensureAnonymousSupportChatThread` → `recordCustomerTurn` → `createSupportChatJob` → `enqueueSupportChatTask` (same Cloud Tasks queue and local-dev inline fallback as the customer-account path). Answers `{ok:true, jobId}`.
- `GET /apps/schedule-rules/support-chat/:jobId?conversationId=...` — polled every 1.5s by the widget. Derives the expected `threadId` from the caller-supplied `conversationId` and compares against the job's actual `threadId`; a mismatch and a missing job both answer the byte-identical `404 {ok:false, reason:"not_found"}` (anti-enumeration, same posture as the customer-account poll route).

**Widget implementation is a vanilla-JS port of `extensions/support-chat/src/SupportChat.jsx`'s enqueue-then-poll and block-rendering logic** — no Preact/bundler available in a theme app extension. Same constants (1.5s poll interval, 60s foreground timeout, 4-minute background-continuation poll for a turn that finishes after the client gave up), same `switch(block.type)` renderer for `text`/`products`/`slots`/`choices`/`order`/`summary` (summary renders plain text, no Confirm button, defensive even though `ordering:false` already makes the affordance server-side unreachable), same `[TAP] <payload>` convention for slot/choice chips. No session-token fetch (unlike the customer-account extension) — App Proxy auth is the signature Shopify's edge computes, not a bearer token the client manages.

**Consequence:** Postgres model count 12 → 13 (new `AgentRateLimit`; `SupportChatThread` gains a `channel` column, default `"customer-account"` so existing rows are unaffected); extension count 11 → 12 (`extensions/storefront-chat-widget`, the first `type = "theme"` extension in this repo); two new App Proxy routes added to the app-proxy route table in [api.md](./api.md); zero Shopify order writes, same as every other agent-core surface — everything lands in the `SupportChat*`/`AgentRateLimit` Postgres models only.

**Live-verification sequence actually followed (both halves passed same-day, see [verification-log.md](./verification-log.md)):**

1. **Backend alone, before any frontend work:** a Node script hand-computed valid App Proxy signatures (same HMAC scheme `verify-app-proxy.server.ts` checks) and hit the real deployed Cloud Run route directly — confirmed a bad signature 401s before touching the database, a real turn resolves to a genuine LLM reply (a Makati delivery-fee question), a mismatched `conversationId` on poll returns the anti-enumeration 404, and a `CONFIRM_ORDER_...` payload is intercepted before ever reaching the LLM.
2. **Widget + real browser**, on a throwaway unpublished draft theme first (`Modernize spacing backup`, zero customer-traffic risk), then the same app-embed toggle saved on the actual active/published theme (`VERIFY-dynamic-cta`) once the draft-theme run proved correct — a product-search turn on the live site returned real product cards (image, title, ₱ price) linking to real `flowercart.store/products/*` URLs, and a delivery-cutoff question returned a correct, correctly-toned answer, both against production traffic.

## ADR-22 — Durable DeliverySyncTask rows + Cloud Tasks worker replace the inline orders/create sync (Phase A of the async-jobs design)

**Date:** 2026-08-26 · **Status:** Implemented (Phase A), NOT yet deployed. 1043/1043 tests (+40), typecheck/lint/build clean.

**Context:** The 2026-08-26 Orders Ops review left three deferred findings (M1: a transient failure anywhere in the orders/create handler — including a Neon cold start on the schedule-rules read — was a permanent, silent loss of the delivery sync, which then undercounts booked-slot capacity forever; S5: a partial sync — tags without metafields, or vice versa — left no marker anywhere; S4: 100-order bulk ops in one request). The merchant identified the shared root cause: one HTTP request holds too much work with no durable record of progress, and directed a design-first approach before any code.

**Decision — the row is the resume point:** New `DeliverySyncTask` Prisma model (migration `20260826000000`): one row per (shop, order) with the extracted work input, a per-step ledger (`metafieldsDone`/`tagsDone`/`codFeeDone` — steps with nothing to do are created already-true), `status`/`attempts`/`lastError`, a `lockedAt` worker lease, and a `nextAttemptAt` sweep marker. The webhook (`webhooks.orders.create.ts`) is now a THIN receiver: extract → upsert row → enqueue → 200; its only intentional non-200 is the row upsert failing, where it throws so Shopify's own redelivery is the durable fallback. The worker (`webhooks.delivery-sync_.worker.ts`, Cloud Tasks, 200/503 contract) runs the steps via `processDeliverySyncTask()`; an hourly sweep (`internal.delivery-sync-sweep.ts`, Cloud Scheduler) rescues stranded rows; a warning banner on `/app/orders` (guarded `syncIssues` loader field + `retryDeliverySync` op) surfaces failed/stuck rows to the merchant — nothing is silent anymore. Posture: work BOOKKEEPING only — the Shopify order stays the delivery-state ledger.

**Decision — merchant constraint (1), no double-processing:** the claim is ONE conditional `updateMany` (`status: "pending"` AND `lockedAt` null-or-stale → set `lockedAt`) — check and take are a single SQL UPDATE, so Postgres row-locking makes the losing worker see count 0 and walk away untouched (lesson: the 2026-08-02 Messenger duplicate-reply incident). Behind the lease every step is idempotent on the Shopify side (`metafieldsSet` set-semantics, `tagsAdd` add-if-absent, COD fee's scan-before-add, and the counts read passes `excludeOrderId` so a retry can't count the order against its own slot), so even a pathological lease overlap only re-writes identical values.

**Decision — merchant constraint (2), a paid order is never rejected for cutoff at retry time:** D4/DEF-7 carried whole — validation stays a flag (`delivery.sync_status`), never a gate, and its clock is the `checkoutTime` FROZEN on the row at webhook time, never the retry time. Retries hours later give the identical verdict the checkout moment deserved. Pinned by test (`test/delivery-sync-task.server.test.ts` "THE FROZEN CLOCK").

**Decision — ride the existing rails, zero new required infrastructure:** the enqueue reuses the shared Cloud Tasks POST core (originally in `messenger-queue.server.ts`; moved to `ops-queue.server.ts` on 2026-09-08, ADR-25) with an ops-secret resolver (`OPS_WORKER_SECRET` → `MESSENGER_WORKER_SECRET` fallback; same resolver on sign and verify sides so they can never disagree) and optional `OPS_TASKS_QUEUE_PATH`/`DELIVERY_SYNC_WORKER_URL` overrides. Retry pacing is split deliberately: Cloud Tasks' queue backoff paces worker retries (worker 503s on transient failure); `nextAttemptAt` (1m/5m/15m/1h/3h/6h/12h, attempts cap 8) paces only the sweep. "No offline session" fails terminally instead of burning retries.

**Consequence:** Postgres model count 13 → 14; `webhooks.orders.create.ts` no longer performs any upstream call besides `authenticate.webhook`; api.md §2 row 1 and the orders/create failure contract rewritten; the ops page gains its first non-order loader enrichment consumer surface (the sync-issues banner). Phases B (bulk-action jobs) and C (pending tasks counted into booked counts) are approved in the proposal but deliberately separate deployments.

**Phase B addendum (2026-08-27 — implemented, NOT yet deployed; closes S4):** every `/app/orders` bulk op's execution extracted into ONE shared executor (`executeBulkAction`, `services/bulk-actions.server.ts` — mutations, per-op loops, and result types moved verbatim from the route; the route re-exports the types so `useBulkActions`' import path survives). The action validates params first (400s and the REC-4 capacity round-trip are unchanged and always synchronous), then splits: **≤ 10 orders run inline exactly as before; more become a `BulkActionJob` + per-order `BulkActionJobItem` rows** (models 14 → 16, migration `20260826010000`) answered as `{ mode: "job", jobId }`. The Cloud Tasks worker (`webhooks.bulk-action_.worker.ts`) processes **chunks of ≤ 15 items and re-enqueues itself** between chunks — cooperative chunking, so no request ever again outlives the embedded fetcher/Cloudflare window. Same §2a guard stack as Phase A (job lease via conditional updateMany renewed per chunk; items claim pending→processing; stale-processing reset only by the lease holder) plus three op-level retry-idempotency upgrades pinned by tests: already-cancelled → success, nothing-fulfillable-and-FULFILLED → success, and reschedule skips when metafields sit EXACTLY at the target (exact compare, deliberately NOT the canonical matcher, so drifted spellings still get their §5 repair write — that distinction is what keeps `orders-reschedule-capacity.test.ts` green). Client: `useBulkActions` polls `GET /app/orders/bulk-job/:jobId` every 2s, renders a progress banner, and fires the same completion toast/selection-prune/revalidate as the inline path; the job survives a closed page (only the toast needs the page open). The hourly sweep also rescues stranded jobs; finished jobs purge at 7d (and done sync tasks at 30d) via the nightly chat-retention job.

**Phase C addendum (2026-08-27 — implemented, NOT yet deployed; closes the last M1 capacity hole):** the booked-counts engine (`delivery-bookings.server.ts`, ADR-12) now overlays each shop's still-pending `DeliverySyncTask` rows onto the Shopify scan — a paid order whose sync hasn't landed yet has no `custom.date` metafield, so the scan alone undercounted it for the whole retry window. Semantics are carried by the query itself: `status: "pending"` AND `metafieldsDone: false` (once the metafield step succeeds the scan sees the order — the overlay row would double-count) over tracked dates only; a belt-and-suspenders dedupe by order id against the scan closes the metafields-landed-mid-cache-window edge. Overlay rows ride the same `DeliveryBooking` shape, so `deriveBookedCounts`' `excludeOrderId` applies to them for free — the sync worker evaluating its own order's capacity still cannot count that order against its own slot. ADDITIVE and fresh on every call (never cached — the 60s cache still holds only the Shopify scan), fail-open on Postgres trouble (scan-only counts + warn, the pre-Phase-C baseline). This is deliberately NOT a local cache of booked counts — the ADR-12 "computed live" posture stands; the overlay only adds rows the live scan cannot see yet, and each row leaves the overlay the moment its metafields land. All consumers (webhook worker capacity evaluation, merchant/customer reschedule, scheduler page) inherit it through the single `getDeliveryBookingsSnapshot` chokepoint. No migration; no new env. ADR-22 is now fully built.

## ADR-23 — Customer self-service reschedule closes at the slot's own last-order instant; merchant sees customer reschedules through a Seen-marker banner, not notifications

**Date:** 2026-09-04 · **Status:** Implemented and DEPLOYED the same day — commit `191bebc`, Cloud Run revision `delivery-scheduler-00269-9f8` (100% traffic), live-verified on the prod Orders Ops page (banner, hidden-search hint, badge time); the slot gate is unit-tested, not yet live-exercised. 1087/1087 tests (+26), typecheck/lint clean. Backend-only change (no extension, toml, or migration).

**Context:** Order #4292 (Sep 4, 9AM-12PM) was rescheduled by the customer to Sep 28 at 8:47 AM on delivery day — 13 minutes before its window — after the merchant had prepared it. The write itself was correct on every surface. Three things were wrong around it: the customer gate (`canRescheduleDelivery`, ADR-10 §5) asked only whether the delivery *day* was still bookable (`cutoffHour` 17), so a morning slot stayed movable long after the storefront had stopped selling it; nothing told the merchant — the order simply vanished from the Today list; and a search for "4292" on the Today tab returned nothing because the dated tabs apply their client-side date filter on top of the search (the order was already Sep 28). The merchant's framing: visibility is the main problem, the gate is the one guard needed so the near-miss cannot repeat.

**Decision — one gate, reusing the rules that already exist (no new function, no new config):** `canRescheduleDelivery(date, now, rules, timeSlot?)`. When the caller supplies the booking's current slot, the gate also requires `now < getSlotLastOrderInstant(rules, date, slot)` — the identical "slot start minus `prepHours`" instant the storefront and `availabilityWindow.slots[*].lastOrderAt` already use. "Still sellable ⇒ still movable" now holds per slot, not per day. An unparseable slot falls back to the day-level answer (never lock on bad data). The customer route passes `getCurrentDeliveryTimeSlot(order)`; the merchant override path is untouched (ADR-10 §5: merchant gates are data-integrity only). `isSlotAvailable` was deliberately NOT reused for this: it also checks blocked/capacity of the current slot, which would wrongly lock an order that is itself occupying a full slot. Rejected alternative: "no same-day reschedule at all" — a policy call the merchant can still make by config (`prepHours`) or a later flag; the slot-level rule matches what the customer already sees on the storefront.

**Decision — visibility on `/app/orders`, three pieces:** (1) a **"Rescheduled today" banner** on every tab listing customer reschedules from the last 48 hours that the merchant has not marked Seen; each row shows order, customer, from → to, shop-local time, source, **Open** and **Seen**. (2) a **hidden-search hint**: when a search on a dated tab (or with a date/slot filter) yields no displayed rows but the loaded page has hits, name them and offer "Show in All". (3) the **reschedule time on the badge**: the row's `resched` badge and the panel's Delivery status badge read "Rescheduled · 8:47 AM" (or "Rescheduled · Sep 3, 5:09 PM").

**Decision — Seen is a `$app` order metafield, keyed by the event timestamp:** `markRescheduleSeen` writes `$app.reschedule_seen_at` = the acknowledged event's `requestedAt`. Why not the alternatives: `localStorage` is per device and per person (a VA's click would not clear the merchant's banner); a Postgres table needs a migration plus deploy-time `prisma migrate deploy` for a checkbox; a tag (`resched-seen`) is visible everywhere tags are and cannot distinguish a second reschedule of the same order. The timestamp key means a newer reschedule (later `requestedAt`) resurfaces on its own. It is an order write but NOT a delivery write — api.md §2 fields untouched, no reader outside this loader consults it. Failure contract follows ADR-11 (200 + ok:false upstream, 400 on bad input).

**Decision — data source is the `resched-<day>` event tag, fetched in parallel, fail-open:** the banner must render on every tab, so it cannot ride the page query. A second small query per load — `tag:resched-<today> OR <yesterday> OR <day before>` (three shop-local days so a 48 h window survives the day boundary; tag search is the only server-side handle because metafield terms are ignored by the orders search) — runs in `Promise.all` with the page query and degrades to "no banner" on any error. The exact window, the customer-only source filter (merchant reschedules happen on this page with their own toast), and the Seen marker are applied by the pure lib `app/lib/recent-reschedules.ts`, unit-tested. Shop-local time labels are stamped in the loader, not the browser, because the client has `todayISO` but not the timezone (orders-ui.md §6 rule).

**Deferred (not built):** merchant email on customer reschedule via the existing SMTP path — the banner covers the ops loop the merchant described; email can be added later without touching the write path. Also deferred: retiring or hardening the dead App Proxy reschedule route (known-issues), which still carries the day-level gate but has no caller.

**Consequence:** `/app/orders` gains a second loader query and a fourth single-order op (`markRescheduleSeen`); `canRescheduleDelivery`'s signature grows one optional parameter with unchanged behavior for existing callers; api.md §1/§2 + diagrams, orders-ui.md §1/§2/§3/§5/§7, changelog and verification-log updated.

**Addendum (same day, 2026-09-04 — merchant request after the first deploy):** (1) **Banner sources widened to customer + merchant** — the merchant reads the banner as the day's reschedule log, so a VA's merchant-side move must be visible to the owner too; the cost is more rows after a bulk move, answered by a **"Mark all N as seen"** action: `markRescheduleSeen` now accepts parallel `orderId`/`requestedAt` pairs (≤50, dedupe per order, `metafieldsSet` chunked by 25) so a 30-order move is one round trip. (2) **Customer notice after a merchant reschedule, on the existing rails** — the merchant asked for the customer (not himself) to be emailed, "if it doesn't need workers or Postgres". It doesn't: the Reschedule modal gains "Email the customer about the new schedule" (default ON — a merchant-side move is the one schedule change the customer did not make themselves, so silence is the surprising option); `BulkOpParams.reschedule.notifyCustomer?` is optional so `BulkActionJob` rows queued before the field parse unchanged; the executor calls `sendRescheduleNotice` (`reschedule-notice.server.ts`) only after a successful canonical write, through the same SMTP transport/From/BCC-self as the compose op, logging the same `EmailSendLog` row so the panel timeline shows "Email sent". Recipient is the order's customer email read in the executor's own state query (E-4 — never client-supplied). The outcome (`sent` / `skipped_no_email` / `failed`) is reported inside a still-successful item: an SMTP hiccup must never read as a failed reschedule, and a worker retry must never re-run the write just to re-send mail. Rejected: emailing the merchant (the banner already does that job) and a send queue (≤100 sends per bulk op against a 500/h provider limit). Not built: a notice on the customer's own self-service reschedule — they just did it themselves in the modal.

## ADR-24 — Dated Orders Ops views query by delivery-date TAG on the server; the 250-newest window is no longer the workable set

**Date:** 2026-09-04 · **Status:** Implemented, deploying the same evening. 1109/1109 tests (+9), typecheck/lint/build clean. Backend only.

**Context:** The Today / Tomorrow / This week tabs and the Delivery date filter were built on a 2026-07-11 finding: Shopify ignores metafield search terms on the orders query unless the definition is indexed as filterable, so the loader fetched the 250 newest orders and the browser filtered them by `custom.date`. That window was the whole workable set. It broke the moment an order was older than the window: #4030, placed Aug 7 and moved by the merchant to Sep 5 after a failed delivery attempt, was invisible on Tomorrow while nine newer Sep 5 orders showed — the merchant found out by counting ("9 showing, 10 sold") and nearly missed a redelivery.

**Decision:** Send the delivery date as a **tag** term. Every synced order carries its delivery date as a bare `YYYY-MM-DD` tag (written by the `orders/create` sync, re-synced by both reschedule paths), and tag search is exact-match — the same property the recent-reschedules banner already relies on (`tag:resched-<day>`). `buildDeliveryDateTagQuery` (`lib/order-tags.ts`) emits `tag:2026-09-05` for one day or a parenthesised OR for a week; `computeDateRefs` / `enumerateISODates` (`lib/date-refs.ts`) are the ONE definition of tomorrow / this week (Sunday–Saturday), used by both the loader and the client memo so the two can never disagree. The client-side metafield filter stays as a safety net; the slot filter stays client-only (slot tags have legacy spelling variants); metafield terms are still never sent. `pageSize` 250 remains, now a ceiling for one day rather than the whole set. Tab counts: a date-scoped page knows only its own view, so `dateScoped` tells the client to show a count on the active tab only.

**Trade-off accepted:** an order with no date tag — manually removed, or whose `orders/create` sync has not landed yet — is absent from the dated tabs until the tag exists (it still shows on All). The manual case is already documented as a side channel in api.md; the sync case is covered by the sync-issue banner and self-heals when the task completes. Rejected: enabling the filterable capability on the metafield definitions (a definition change on live data for the same outcome the tag already gives) and a larger page (still a window, just a bigger one).

**Consequence:** the dated views are now correct for pre-orders and far-forward reschedules of any age; `todayISO` is resolved before the query is built; orders-ui.md §2/§3 updated. Follow-up noted, not built: a "Redelivery" reading of FULFILLED orders whose latest reschedule post-dates their fulfillment (they currently count as Fulfilled in the KPIs and Items to prepare) — the Shopify-native alternative is to cancel the fulfillment when a rider returns a parcel.

## ADR-25 — Meta Business Agent owns the chat; this app exposes an Agent API; the in-repo Messenger bot, support chat, and storefront widget are removed

**Date:** 2026-09-08 · **Status:** Implemented on `feat/agent-api` (commits `e417257`, `6e3d73f`, `763ae34`); typecheck and the vitest suite green (622 tests). Not yet deployed as of this entry.

**Context:** An audit of 31 Facebook inbox conversations (2026-09-07) found that every conversation handled by the Meta Business Agent ended in a human handoff, because the agent could not read order state, quote fees or slots, or create an order. The in-repo Messenger bot (ADR-20/21) had never passed Meta App Review and had no live users. The merchant decided that conversation and knowledge stay in Meta, and that this app should give the Meta agent order-aware tools instead of running its own chat stack.

**Decision:**
- **The Meta Business Agent is external.** No LLM, chat transport, Messenger webhook, support chat, or storefront widget runs in this repo.
- **Three bearer-token routes** back the agent's tools: `POST /api/agent/orders/draft`, `GET /api/agent/orders/status`, `GET /api/agent/delivery/quote` (`services/agent-api.server.ts`). Auth in `lib/verify-agent-token.server.ts`: `META_AGENT_API_TOKEN` with `META_AGENT_API_TOKEN_PREV` for rotation, timing-safe compare, in-process rate limits of 20/min (draft) and 60/min (status, quote).
- **Draft orders carry the same delivery contract as checkout** (`Delivery Date` / `Delivery Time` customAttributes, date and slot tags, `LALAMOVE` shipping line) plus `Agent Idempotency Key`, `_Messenger PSID`, `source:messenger`, and `agent-key-<key>`. Idempotency is a search for the `agent-key` tag before create. Once paid or completed, the order flows through the unchanged `orders/create` sync.
- **COD is completed immediately**: after checking the NCR area and the amount window from the same `$app:cod-eligibility` function-configuration metafield the checkout Function uses, the draft gets the `COD-FEE` variant line and `draftOrderComplete(paymentPending: true)`. The webhook's fee step stays a no-op for these orders because `applyCodFeeToOrder` skips an order that already carries the SKU.
- **Status is order number + email**, for every Shopify order, via `lib/order-tracking.server.ts`. No phone fallback.
- **Merchant deep link**: `META_PAGE_ID` + the order's `_Messenger PSID` build the Business Suite inbox URL shown in the `/app/orders` panel Actions menu and Customer column. Messenger only; Instagram was left out by merchant decision.
- **Removed**: Messenger webhook/worker routes, `agent-*` and `messenger-*` services, support-chat routes/services/worker, widget config, chat retention, order lookup, COD/FAQ facts, `/app/messenger-orders`, `extensions/support-chat`, the `@anthropic-ai/sdk` dependency, and eight Prisma models (`MessengerThread`, `MessengerMessage`, `LookupAttempt`, `AgentRateLimit`, `SupportChatThread`, `SupportChatMessage`, `SupportChatJob`, `WidgetConfig`; migration `20260908000000_drop_messenger_and_chat`). Seven models remain.
- **Kept and renamed so the ops rails survived the removal**: the Cloud Tasks core became `services/ops-queue.server.ts` (`OPS_*` env first, `MESSENGER_*` fallbacks, worker header name unchanged so in-flight tasks still verify); the HMAC verifier became `lib/verify-hmac-signature.server.ts`; `messenger-coverage.server.ts` became `delivery-coverage.server.ts`; the theme extension became `delivery-fee-checker` (same uid) with the chat app-embed removed; `lib/shop-domain.server.ts` resolves `SHOP_DOMAIN` with the legacy names as fallbacks. The manual draft-order form stays at `/app/manual-order`.

**Consequences:** ADR-20, ADR-21, and the ADR-21 addendum are superseded and kept as history. `docs/architecture.md` and `docs/api.md` were re-verified against the code on 2026-09-09. New env: `META_AGENT_API_TOKEN`, `META_AGENT_API_TOKEN_PREV`, `META_PAGE_ID`, `SHOP_DOMAIN`, `OPS_WORKER_BASE_URL`, `STATUS_PAGE_BASE_URL`, `CUSTOMER_ACCOUNT_URL`. Deploy order that matters: back up Neon before `prisma migrate deploy` drops the eight tables; set the `OPS_*` variables in Cloud Run before deleting the `MESSENGER_*` ones; remove any scheduler job for the deleted `/internal/chat-retention` route.

**Addendum (2026-09-09) — review fixes and release.** The Codex review of PR #2 raised two P1s (the `agent-key-<key>` tag exceeded Shopify's 40-character tag limit for keys longer than 30 characters; the read-before-create idempotency check let a retried tool call create two drafts) and several P2s. Fix `f43d413`: a new **`AgentOrderRequest`** model (migration `20260909000000_add_agent_order_request`) claims the idempotency key with a unique insert before any Shopify write (`409 in_progress` on a concurrent retry, takeover of a pending row after two minutes, COD completion retried from a drafted row), long keys are hashed into the tag, every draft is checked against `checkDeliveryCoverage`, variants must be `availableForSale`, COD area matching mirrors the checkout Function (ZIP ranges, exact normalized city with the alias table, province guard) with the Function's 2500 default minimum and fail-closed behaviour when the config cannot be read, and more than 10 items is a validation error. Postgres is therefore **eight** models, not seven. **Released 2026-09-09:** Cloud Run revision `delivery-scheduler-00278-2fh` (migrations `20260908000000_drop_messenger_and_chat` and `20260909000000_add_agent_order_request` applied) and Shopify app version `delivery-scheduler-97` (support-chat extension removed, `delivery-fee-checker` in place). ## Messenger Agent — Phase Deviations Log (moved from messenger-progress.md)

> **Historical.** The Messenger bot was removed 2026-09-08 (ADR-25) and `docs/messenger-progress.md` was deleted with it. The entries below describe code that no longer exists.

**Note:** `docs/messenger-progress.md` is a phase-by-phase build/handoff log (gate result, evidence, files touched, open questions). Its explicit decision-and-rationale content (the "Deviations" sections, and the LLM provider choice) is consolidated here per the docs/decisions.md-is-the-only-rationale-doc convention; the rest of that log (gate results, evidence, file tables, open questions) stays there untouched.

**Phase 4 — LLM provider (2026-08-01):** Claude Sonnet 5 via `@anthropic-ai/sdk` was the merchant-approved provider, pinned in `messenger-llm.server.ts` (the one provider-swap file).

**Phase 4 deviations:**
1. **Official Anthropic SDK** (not plain fetch like the Messenger side): the master doc's "no SDK wrapper" rule targets the Messenger/Graph transport; the LLM sits behind a thin interface, so the SDK stays a one-file swap.
2. **Slot quick replies auto-attached by code, not the LLM**, from the turn's last successful `get_available_slots` call — "the LLM handles language; the code advances state."

**Phase 3 deviations (2026-08-01, Queue + Neon):**
1. **HMAC task auth instead of Cloud Tasks OIDC.** The GCP-idiomatic OIDC token verification would need `google-auth-library` + a JWKS fetch; HMAC on the task payload (same `sha256=<hex>` format as Meta's, same tested verifier lib) is zero new dependencies. The worker URL is public, but every task is signed.
2. **Prod Neon repair not part of the original plan:** the `_prisma_migrations` table went missing from the prod DB (P3005 on any new revision boot; cause unknown, not from the repo). Merchant-approved fix: baseline ×3 via `prisma migrate resolve --applied` + `migrate deploy`.
3. **TEMP `[force-timeout]` gate hook** (45s stall after send): deployed on `00177-9xt` to prove the gate, removed immediately on `00178-trn`.
4. **Inline fallback when no queue is configured:** not in the master doc; added so local dev works without a Cloud Tasks emulator. Prod always has the queue configured.

**Phase 2 deviations (2026-08-01, Echo bot):**
1. **Inline send before the 200,** not fast-ack-then-process: the master doc says "return 200 fast, before any processing," but RR7/Cloud Run has no `waitUntil` — once the response returns, Cloud Run throttles CPU and kills fire-and-forget work (the exact trap the master doc's own Phase 3 note warns about). So Phase 2 verifies, processes, and `await`s one echo send (5s timeout) before the 200 — one Graph call, well under Meta's delivery timeout. True fast-ack + enqueue arrived in Phase 3 (Cloud Tasks).
2. **Malformed JSON with a valid signature answers 200, not 400** — Meta cannot fix a malformed redelivery body; logged only.
3. **Echo truncated at 2000 chars** — Messenger's hard text limit; not in the literal spec but needed so a long echo isn't rejected.
4. **No dedupe in Phase 2** — `mid`-unique dedupe is Phase 3 (Neon); a Meta redelivery could double-echo, accepted for an echo bot.
5. **Progress handoff kept in the repo** (`docs/messenger-progress.md`) rather than the Drive folder, since `flowercart-messenger-build` wasn't synced to this machine yet; the human uploads to Drive separately.
6. **Page token proxied by Claude (2026-07-27, explicit merchant authorization).** The master-doc rule "human pastes secrets only" was waived by the merchant to unblock the gate: Claude generated the token in the Meta dashboard, stored it in Secret Manager (v2), and updated Cloud Run. The token passed through the Claude session context. Obligation recorded at the time: rotate `messenger-page-token` before declaring production-ready — closed 2026-08-03 (the merchant generated a new page token in the Meta dashboard and uploaded it directly to Secret Manager, bypassing Claude).

**Phase 8 deviations (2026-08-03):**
1. **Profile-setup success/failure feedback uses the App Bridge toast** (`useAppBridge().toast.show`, same idiom as the scheduler op-plumbing) — the brief said "toast"; this is the closest existing pattern in the repo.
2. **Ice breakers use the locale-wrapped shape** (`[{ locale: "default", call_to_actions: [...] }]`) because that is the current Graph API format (the flat `[{question,payload}]` shape is the old v7 form).
3. **Typing indicator is `void` fire-and-forget** (not awaited): the send is never-throws by design, and the worker request stays alive while the LLM turn runs, so it isn't cut off by Cloud Run CPU throttling.

**Phase 10 deviations (2026-08-03, add-on upsell + follow-up):**
1. The add-on is a **required step** in the state machine, not an optional flag — the simplest way for the code (not LLM memory) to guarantee the one-time offer; "decline" is a first-class decision.
2. Follow-up favors **zero-duplicate over guaranteed delivery**: if the send fails after the claim, it is not retried — it's a nudge, not a transactional message.
